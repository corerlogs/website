agent 写完九成代码之后，人剩下的是证据

一个工程师怎么给写代码的 agent 装上验证回路，三种测试各自会被什么骗过，以及一次 42 毫秒的差分测试实测。文中每个数字都标了来源。

一个人能同时盯住几个 agent，取决于他能不能不读 diff 就确认对方做对了。下面是我自己跑过的那一套，以及每一条证据会被什么骗过。

一、瓶颈从键盘挪到了确认#

先说那个我复核不了的数字。Claude Code 团队说，团队里绝大多数代码由 Claude 写、也由 Claude 评审，比例约九成。厂商公布，我这边没法复算，它只能说清方向。写代码不再是最慢的一环。

没有验证手段的时候，一个人能同时管的 Claude 是一到两个，因为每一行都得自己看。有了验证手段，几十个甚至上百个可以一起跑。模型速度没变，变的是每个 agent 能自己交出证据。

同一份材料里还有一个数字。做结构化文件生成时，让一个独立的 grader 按 rubric 打分，比标准的提示词循环最多提升 10 个百分点的任务成功率，难题上提升最大。同样是厂商公布。

写代码便宜之后，卡住流程的地方换了。

今天的坏法后果
人读每一个 diff并行度封顶在一两个
单测全绿，功能坏了agent 和测试出自同一个理解，一起错
门禁写在 PR 里本次改动顺手把门禁改宽

二、三种测试，各自能被什么骗过#

先记两条失败模式，跟测试类型无关。测试 flaky，agent 就学会重跑，修代码这一环被绕过。测试慢，一批里能跑的次数变少，出问题时定位反而更难。重的测试放在改动落地之前跑。

端到端测的是真实用户流程，加一件商品进购物车、结账、走到确认页。它难被骗，因为整个功能要么能用要么不能用，而失败时能给你一张截图和一句哪里坏了。单元测试失败只能说 Error: Timeout after 30 seconds。代价是慢，还有 flaky。跑它的方式值得讲究，用 Chrome 扩展、模拟器或者 API harness 给 agent 一双真的手和一个真的眼。

属性测试处理的是你没想到的那半边。先写一句你认为不可能错的断言，然后让库去生成上千个输入推翻它。JS 用 fast-check ，Python 用 Hypothesis ，Rust 用 proptest 。四类属性几乎每个项目都有。

属性一句话
往返编码再解码，拿到原来的东西
不变量余额永远不会变成负数
幂等迁移、归一化、重试做两遍和做一遍一样
等价优化版和朴素版给出同一个结果

差分测试拿旧系统当标准答案。同一批输入喂给新旧两个实现，输出不一样就是 bug 或者破坏性变更。它在大型迁移里最有用，因为那时候唯一还能信的行为描述就是旧系统本身。输入要用随机生成或者生产流量抽样，无关差异（空白、字段顺序）要归一化，确实该不一样的差异要列进已批准变更。

类型它回答什么最容易骗过它的做法
端到端整个功能能不能用，坏在哪一步用例太少，靠固定 sleep 等待，变 flaky
属性边界输入下有没有反例属性本身写错，比代码还自信
差分新旧行为究竟哪里不一样旧系统自己就有 bug，被当成正确答案

三、实测，8 条手写用例全绿，129 条随机输入悄悄变了#

举一个我在这里跑过的例子。一个 tag 归一化函数要重写。旧版只保留 ASCII 字母和数字，新版把正则从 [a-z0-9] 换成 \w，看起来只是放宽一点。

重写的人按自己的理解写了 8 条用例，空格、连字符、大写、首尾杂字符都覆盖了。然后我拿旧实现当 oracle，跑 5000 条随机输入。

第一版的随机生成器把怪字符塞得太勤，一半以上的输入都不一致，那不可能是真实日志的样子。把概率压下来之后，才有下面这组数字。

== hand-written suite
  8/8 agree

== differential over 5000 random inputs
  616/5000 disagree (12.3%)
  of those 487 are the approved `_` change, 129 are not
  42 ms total, 8 us per input

== smallest unapproved counterexample
  'üe' old='ue' new='u-e'

手写用例 8 条全过。5000 条里 616 条两边不一样，其中 487 条来自一个事先批准过的变更（新版把下划线当分隔符），剩下 129 条（2.6%）没人批准过。跑完 42 毫秒，一条 8 微秒。

我原本以为最小反例会是一个带变音符的库名，结果只有两个字符，'üe'。旧版先做 NFKD 分解再丢掉非 ASCII，得到 ue。新版的 \w 不认组合音标，把那个音标当成一个分隔符，得到 u-e。同一个 tag，两个 URL。

两个实现各十几行，可以自己抄走。

# experiment/difftest.py：旧版只留 ASCII 字母数字
def old_normalise(raw: str) -> str:
    s = unicodedata.normalize("NFKD", raw.lower())
    s = s.encode("ascii", "ignore").decode("ascii")
    return re.sub(r"[^a-z0-9]+", "-", s).strip("-")

# 新版把 [a-z0-9] 换成 \w，看起来只是放宽
def new_normalise(raw: str) -> str:
    s = unicodedata.normalize("NFKD", raw.lower())
    return re.sub(r"[^\w]+", "-", s).strip("-")

这段代码的用处在这个例子之外，它可以喂真实流量。抽 5000 条生产日志里的输入，42 毫秒跑完，结论不依赖谁去读代码。手写的那 8 条用例漏掉了变音符，因为写用例的人和新代码出自同一套理解，随机输入没有。

四、把「跑起来」写成一条 skill#

团队的说法是，跑一遍端到端比跑测试更重要。iOS 的改动不会不去模拟器里点一遍，Claude 的改动同理。

做法是在仓库里建一条叫 verify 的 skill，放在 .claude/skills/ 下，离相关代码越近越好，需要几条就建几条。Claude 知道在提交之前该用它。web 改动用 Chrome 扩展，移动端用 iOS 或 Android 的 MCP，桌面用 computer use，后端就在本地把服务起起来。

这条 skill 要快、要稳。慢的 skill 会被跳过，跳过几次就没人修了。让 Claude 反复迭代它、压它，它是你的冒烟测试台。

<!-- .claude/skills/verify/SKILL.md：一条 skill 的形状 -->
---
name: verify
description: 提交任何改动之前，把应用跑起来并走完一条用户路径
---
1. make dev，等到 127.0.0.1:8080/healthz 返回 200
2. npx playwright test e2e/smoke --reporter=line，失败就存截图
3. 截图里能看见用户走完那一步，才算过

检查连续三轮修不好，Claude 停下来，把问题交给人。这条规则省下来的是人的注意力，衡量单位不是 agent 的时间。

五、检查项要有一个能从 diff 读出来的触发条件#

团队维护一张 39 条可靠性清单。每条带三样东西，一个能从 diff 读出来的触发条件、一个检查、以及它背后的事故或 PR。

举个例子，--resume 要能读旧 transcript。触发条件是会话存储或消息类型出现在 diff 里。碰到它，就问新加的字段在旧 transcript 里缺省时还能不能读。

Claude 读 diff，只跑触发条件对得上的条目，通常 3 到 10 条。没人需要背住去年的故障。

大部分门禁死于同一个原因，被要求记住太多。39 条一起跑，慢、噪声大，人开始不看结果。

六、门禁要放在被审改动够不着的地方#

一个改动能改判它的那把尺子，这把尺子就废了。Code Review 从主干（默认分支）读 REVIEW.md，不从 PR 里读。团队把这条做成了机制，能卡住改动的规则放在改动动不了的分支上。

评审只对 commit 有效。有人一边推一边审，评审结果立刻作废。

每条 commit 盖一个章，写明它是怎么被验证的，章里甚至有 none，这样「没验证过的提交」是可以查出来的。团队另外做了一道提交门禁，能挡住一次既没跑 /code-review 也没跑 /verify 的会话。它有 off、observe、enforce 三档。observe 只记日志，记下「本来会被挡住」的那次，用来找假阳性。enforce 真的挡。一次会话里被挡两次之后，下一次放行，免得 Claude 卡在原地。

顺序也有讲究，便宜的检查先跑。agent 在本地没测就推上来，花的是大家共用的评审和 CI 时间。测试、构建、lint 在开 PR 之前跑完，用 hook 卡住，或者给一个测试全过的 /goal。

还有一条，团队的做法和直觉相反。不要靠叠评审来提升质量，在第一个评审上面再压一个更贵的，常常不如把第一个调好。团队的做法是一份 REVIEW.md，写清这段代码该看什么，每一轮用上一轮的上下文，不从零重查。这样更便宜，也找得更多。

七、漏掉的 bug 要变成规则，规则要定期删掉#

第一种，从人的评审意见和 revert 里提炼模式。一条模式要进清单，至少出现在两个 PR 里，并且能从 diff 判断出来。写进去之前，三个 agent 试着推翻它，最后由人在 PR 里批。第二种，拿一个已知事故对应的 PR 回放三个找 bug 的 agent。至少两个找到，这个 bug 就是可检测的。小 diff 上找不到，说明清单缺一条，补进去。

flaky 的测试同样处理。Claude 不能跳过它，不能加 sleep，也不能重试到绿。找不到根因就删掉这条测试，并写下为什么删。

规则会自己长大。测试集、验证步骤、.md 文件，放着不管只会变多，所以要定期清，不然清单本身就是噪声源。

评审本身也要被复查。团队盯三个比例，合并后被 revert 的、合并前被维护者拒掉的，外加一批大小匹配、一直没出事的改动当对照。做正式评测时，他们把仓库回放到评审那一刻的状态，给每个例子配一句「真正的 bug 是什么」的答案，只有准确说中那个 bug 的发现才得分；再用合并且稳定的改动做对照，防止乱报。

召回分三段看，原始发现、验证之后、最终评审。三段分开，才知道系统有没有把自己已经找到的 bug 丢掉。最后把召回一直调到「再提一点就是在拟合评测集」为止。

八、代价、能自己跑的一步、答不上的问题#

决策备选理由代价
先端到端再合并只跑单测单测全绿也可能整个功能坏慢，偶尔 flaky，得养着
差分测试用旧系统当 oracle重写一份规格规格已经和生产漂开了旧系统的 bug 会被当成正确答案
门禁读主干上的 REVIEW.md门禁跟着 PR 走否则改动能改自己的判据改规则要单开一个 PR
新门禁先开 observe直接 enforce假阳性会平白挡住人观察期要多花一次人工看日志
一个评审多轮叠第二个评审叠上去的是成本，不是判断主评审本身要调对

轮到你自己动手，一个下午够用，只要那对函数还在手上。找出你最近重写过的一对函数，旧版本还在生产上跑的那种。把两个实现放进同一个进程，喂五千条真实日志里的输入，把不一致的分成两堆，事先批准的变更一堆，没人批准的一堆。第二堆的数量就是这次重写欠下的账，而它花的是 CPU 时间。

两个我答不上来的问题。差分测试依赖「新旧行为应该一致」，对随机数、时钟、并发顺序参与的系统，这个前提怎么写成一条能跑的规则，我还没找到能用的办法。observe 期结束的时候，哪些假阳性该改规则、哪些该改代码，目前靠人判断，这个判断能不能记成数据，我答不上来。

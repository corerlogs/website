先造一道题，再谈 bench

别急着建榜。你自己的 agent 轨迹里就埋着终端类评测题，找、切、造环境、跑、看轨迹，五步能把一段真实的失败变成一道 terminal-bench 级别的题。

一个 bench 的分数，撑死是几十道题的平均值。稀缺的是其中某一题里那段 gap 还在不在。

一、gap 长在你自己的 session 里#

James Zhu 十一月二十七日在 X 上写了一篇《大bench时代生存指南》，讲的就是这条路。他做的是 Benchmarks’ Last Exam，日常干的活是拆别人的题。开场是一句劝，造好一道高质量的题，比上来就造一个 bench 值钱。

场景是这样的。你让 AI 做一件正事，它在工作区里拉了一坨大的，你一句句纠偏，一百轮之后它端出来的东西勉强能用。这个 session 对你是结束了，对出题的人刚开始。

一段这样的 session 里混着几种「没做好」，得先分开再谈出题。

没做好的原因轨迹里长什么样能不能出题
context 没给足关键约束是你在第五十轮才补上的不能，题面写清楚就没了
能力确实不够犯错前它已有足够信息，却选了一个看似合理的错解能，这是原材料
偶发换个 session 同样的话它做对了先攒样本
没人说得清你和它都不知道怎样算对不能，先写判分标准

第二行原文写得更细。这道题的难，不能来自「用户事后才补充的要求」，得让人仅凭犯错前已有的信息，就有机会发现或者避开它。

值不值得造，看两个乘数，模型表现和人类专家预期的差距有多大，以及这个问题有没有经济价值。两个都大，才值得动手。

二、找，让 agent 翻你自己的轨迹#

轨迹就躺在硬盘上。Claude Code 写在 ~/.claude/projects/ 里，一个工作目录一个 .jsonl；Codex 写在 ~/.codex/sessions；pi 写在 ~/.pi/agent/sessions。这台机器上这三个目录的 .jsonl 加起来 100 个。

别自己读。把筛选条件丢给 agent 跑一遍，你只看它交上来的候选。原文的四条特征在这里。

  • 用户指出产出结果不理想，且返工后结果发生明显变化
  • 用户与 agent 在某一问题上多轮交互，且 agent 在该问题上有长程运行轨迹
  • 困难不是因为用户信息没给全，能定位一个具体、看似合理的错误决定
  • 任务有明确的输入、交付物，以及可检验的好坏标准

筛完你还得过一遍眼。这四条只认形式，不认价值，「你所在领域里值钱又难」那半句得你自己补。

三、切，从犯错的前一刻切到不满意的产物#

一个 session 里杂七杂八，查文献、设计实验、跑计算、写稿。真正让 gap 出现的往往只是其中一段。

切的起点是模型犯错的前一刻，终点是那个不满意的产物交付完。两头都落在轨迹的具体某一行上，不能靠感觉。

现在的模型没那么傻，绝对意义的「犯错」不好找，多数是「选了一个合理的错解」。原文建议让 agent 帮你定位，你负责确认这一段是个有明确输入和输出的任务雏形。

四、造环境，把那一刻还原成镜像#

还原分两块。一块是起点之前模型知道的所有东西，浓缩成一段 instruction 加一个起始 workspace。另一块是任务要用的依赖，blender、lean 这类专业软件和库，打进一个镜像。

格式照 terminal-bench 来。它现在一题一个目录，五样东西。

my-task/
├── instruction.md      # 给 agent 的题面
├── task.toml           # 元数据、资源、超时
├── environment/        # Dockerfile，起始 workspace
├── solution/           # solve.sh，oracle 满分解
└── tests/              # test.sh，判分

task.toml 里真正要填的几行，取自仓库里那道 bun-sourcemap-leak，2.2.0 版。

[metadata]
expert_time_estimate_hours = 1.5

[verifier]
timeout_sec = 600.0

[agent]
timeout_sec = 28800.0

[environment]
cpus = 2
memory_mb = 4096
storage_mb = 10240

两个超时别混。28800 秒是 agent 一次 trial 的上限，八小时。600 秒是判分那一步的上限。

expert_time_estimate_hours 填 1.5，因为 TB 的收录标准是一个知道答案的专家几小时内能做完。指南还补了一句，难度不该由工作量衡量。这个数填到两位数，通常说明题里堆的是步骤。

五、跑，干净上下文#

题面写完不等于题能用。给一个干净上下文的新 agent 跑，看它是不是在你预期的那个点上失败。

干净有两层意思。一层是别用它刚攒的上下文。原文评论区有人担心自己出题自己答容易全对，作者的回答是换个干净的 session，或者开个 subagent。另一层是公平，题面由人来写，环境要可复现，解题需要的材料全放公共环境里，这样每个模型开始时看到的东西一样，这条也是作者在评论区给的。

没复现你的预期，原文列了四种解释。

  • 题面和环境没充分还原当时的失败，让 agent 去 diff 一下
  • 当时是旧模型没做好，新版已经能做对
  • 偶发，多跑几次都能做对，说明这题没难度了
  • 题面提示过头，替模型做了本该它自己做的业务判断

第三条要采样。单次失败说明不了什么，同一个模型跑几轮全过，这题对你手上的模型已经饱和了。TB 的维护规则里，饱和的题在大版本里直接下架。

跑公开集的样子是这样，一条命令起四路并发。

harbor run --dataset terminal-bench@2.0 \
  --agent claude-code \
  --model <model> \
  --n-concurrent 4

自己的题也在这套框架里跑，一次尝试叫一次 trial。

六、verifier，判分器本身也要被考#

分数不能拍脑袋。像高考试卷一样写评分标准，1/0 的通过不通过，或者 0 到 100 的连续分。两头都要防，假阴性误杀好答案，假阳性放过坏答案。再补一个 oracle 满分解，证明这题确实可解。

Harbor 把分写进容器里的一个文件，路径固定。

/logs/verifier/reward.txt      # 一个数
/logs/verifier/reward.json     # 多维或者带标签

TB 的指南对判分器有一句原话。

The verifier needs to be almost perfect, but not provably perfect.

另一条更像判据。两个讲道理的人读完题面，各自写的判分程序应该互相放行同一个解，放不过就说明题面少了东西。指南的原话是 “if two reasonable people read the problem description, a well-specified problem should result in both of them writing verification algorithms so that anyone who passed one of the verifiers would also pass the other.”

拿 LLM 当判官在指南里是例外，不是默认。要用就得证明它几乎不出错，还得写清楚为什么别的办法不行。

七、看轨迹，评测工程就是这个动作#

原文说评测工程的本质就是去看轨迹。让 agent 把模型跑出来的轨迹读一遍，五个问题问下来，改哪里通常就清楚了。

现象说明什么改哪里
没做出来，卡在一个看似合理的错解上难点成立不用改，留着
没做出来，卡在环境装不上setup 有问题镜像
做出来了，路径顺得一模一样题面提示过头instruction.md
轨迹里做对了，被判错verifier 太窄tests
步数都花在同一处这道题的难度落在哪决定要不要切细

八、别为了长而长#

有人问任务跑多长合适，是不是越长程越好。原文的回答是不尽然。几个难点机械地杂糅，每个都做不稳，端到端几乎不可能满足要求，从训练角度看信号太稀疏，也不稳。

它给的分法是一个大任务 A 拆成阶段 B、C、D。B、C、D 单独做都不对，先把它们各自出成题更有价值，没必要一口吃成胖子。单独都对了而 A 还不对，那 A 才值得单独出。

九、原材料是行业 knowhow#

TB 2.0 是 89 道题，仓库里现在 52 个题目目录，公开榜能刷的池子就这么大。

原文的判断更狠一点。最火的榜大概率都被后训练刷过了，不火的榜一般也烂，不然早就火了。所以卷 verifiable bench 之前先问一句，能不能干得比 terminal-bench 更好。内部评测该走在公开榜前面，差异来自 OOD 的新场景，和更多的人工判断。

末尾它还提了一件事。几家模型公司在给科研工作者发免费 token，它们想从你的轨迹里淘题。这件事你自己干更好，workspace 的 context 在你手上。

两个我现在答不上来的问题。

  • 一道题从一段轨迹到能上墙，人工投入的下限在哪，原文没给数。
  • 内部评测和公开榜之间那个差值，多大算正常，没有人公布过。

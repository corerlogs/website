给 agent 一块能抢单的白板：Vercel Board 实测

Vercel Board 是给 agent 用的一块消息板加任务队列。我在本地起了一块，用两个 profile 抢四张卡，记下租约到期、依赖解锁和唤醒延迟的实测数字。

Board 把「谁在做哪件活」变成一次 claim 的返回值，账单是每次操作一次网络往返，我这里是 654 毫秒。

一、Markdown 清单撑到第几个 agent#

一个 agent 干活，待办写在仓库里的 TODO.md 就够。它自己读、自己勾、自己提交，第二天接手的是同一个 agent，文件就是记忆。

三个 agent 同时干，第一件坏事是重复。两个 agent 读同一行没勾的待办，都去修那个 30% 概率失败的 webhook 重试测试，两个 PR 改同一段代码。第二件坏事是状态没有归属。谁在做、做到哪一步、那行字还算不算数，只能靠翻 PR 列表和聊天记录拼出来。

Vercel 内部先把这件事当成了问题。他们跑了一支找漏洞的安全 agent 队伍，让它们读自己的代码库、提修复；又用同一块板子重搭了 v0 的 software factory，这个工厂现在合并超过一半的 PR（官网公布，我没复核）。原文给的理由很朴素，单个 agent 能在 Markdown 里记自己，跨 agent 的时候缺一种原语，用来记任务、委派、状态、日志和已完成的工作。

二、一块板子上有什么#

Board 的逻辑很小，一个消息存储加一套任务状态。

层是什么谁写
channel一个频道，work/ 这样可以带层级前缀人或 agent
thread一条消息和它的回复，报告、进展、PR 链接都在同一条线里线程里任何人
labelkind=bug 这类键值，记录 PR 号或当前状态写消息的人
taskthread 加一个状态，可以被认领任务的所有者
grant谁能对哪个前缀读、写、管理团队管理员

我数了这台机器上 board --help 带子命令的行，一共 49 条命令，核心围绕读、写、任务和授权。命令之外还有两条路进同一个存储，@vercel/board 的 JS SDK，和 npx skills add vercel/board 装给 agent 的说明书。

Claude Code、Codex、Pi、OpenCode、eve、fx、Mastra、LangChain 各有各的会话历史，彼此看不见。原文的说法是它们可以像同一个 harness 那样协作。

三、四件要件，两条原则#

这块板子容易被读成又一个 Trello，要件得先摆出来。

  1. 存储只有一份。同步逻辑写在这里，不写进每个 harness。
  2. 线程是上下文的单位。报告、追查、PR、复审意见留在同一条线里，换一个 agent 接手，读一条线程就够。
  3. 任务是带状态和租约的东西。认领要有期限，人死了或者进程挂了，期限到了自动放回队列。
  4. 权限与审计在板子这一层。谁在哪个频道做了什么，事件里有记录。

两条原则。所有写入都是消息，标签和结构化数据是消息的附件，没有第二种写入口。占用是租约而不是锁，板子不等你报告死亡，它只按时间说话。

四、一次 claim 前后发生了什么#

抢单#

本机跑的，board 0.53.0，vb serve 起的本地板，两个 profile 分别叫 codex 和 fx。先是 codex 抢到，然后是 fx 来抢同一张卡。

$ vb tasks claim 4 --lease 30s --as codex
#4  yours for 30s  Fix the flaky webhook retry test (30% failures on CI)

$ vb tasks claim 4 --as fx
error: Can't claim task #4. Someone holds it.
  #4 is claimed until 2026-11-20T03:48:47.554Z

  See who holds it, and until when:
    vb read 4

被挡回去的 agent 拿到的是到期时间，不是一句「已被占用」。这段错误文案可以直接塞进 agent 的下一轮 prompt，它知道该等多久，或者去干别的。

依赖#

tasks needs 设依赖，complete 的时候只解锁只等它的那些。

$ vb tasks work
#6   claimed    Cap the log reader at 8 MiB per page  kind=bug
#8   ready      Review the retry fix before it ships  kind=review
#10  waiting    Ship the retry fix to production      kind=ship  needs #8

#10 一直挂在 waiting，直到 #8 完成。状态一共七种，waiting、ready、claimed、blocked、completed、failed、canceled，blocked 是把卡按住等人，tasks block 写的理由会留在线程里。

tasks run 把三件事包成一件，认领、跑你给的命令、按退出码 complete 或 fail，跑的过程中自己续租。CI 式的活用它最省事。

唤醒与定时#

--wait 10m 让一个没有活干的 agent 阻塞在那里等。SDK 里是 watcher，一段代码挂在频道上，新事件进来就唤醒一次。

// app/api/board/[[...path]]/route.ts：原文的 watcher，挂 #incidents
const factory = board({
  watch: {
    incidentResponse: {
      tail: "incidents",
      run: async () => { /* 每来一条新事件调用一次 */ },
    },
  },
});

在 Vercel 上，匹配的事件直接唤醒 deployment，中间没有常驻进程，没有活的时候不烧运行时。

vercel board schedule 是反过来用的，agent 自己排一个五分钟后的提醒去查 CI。--no-sync 让这条消息只留在板上，不下发到 Slack。

同步、结构和授权#

Slack 和 GitHub 的双向同步走 SDK 的两个适配器，回复、reaction、编辑、删除都对齐。结构化数据是消息带 schema，注册一个 security-finding@1，post 的时候板子校验，读的人直接取字段，不用正则抠文本。

授权这块我本地只验证了一半。grants create --can 'security/=read,post' 能只给读和写，grants explain 会告诉你哪条规则在生效，我那块本地板给的是 g1 (--all-users) : all，因为它是本机单人板。原文给 sandbox 发权限用的是 sandboxPolicy()，它返回一份 env 和网络白名单，沙箱里没有板子的凭据，只有限定的频道和动作。

五、取舍与代价#

决策备选理由代价
用一个消息板当总线共享文件系统、git 里的待办一个存储，多个 harness 都能写，审计自然落在事件里每次操作一次网络往返，我这儿一次 CLI 调用中位 654 毫秒
租约强锁、单个协调者进程挂了自动释放，不需要谁来判断死亡租约到期不等于人还在干。那次 30 秒的租约，fx 在 29.6 秒后就把卡接走了，同一件事可能做两遍
轮询式唤醒（--wait）长连接推送部署环境无状态，事件唤醒进程建单到拿单 1.2 秒，不是零，高频短任务会看到这个延迟
Slack、GitHub 双向同步只做单向镜像人在聊天窗口回一句也能推进每一处都要对齐编辑和删除，边界比单向多一倍
实验性发布等到 GA先让愿意的人跑起来API 会变，0.53.0 这份 help 就是当下的契约

租约把「谁在做」这件事从协议层面降级成了时间戳，好处是没有共识开销，坏处是没有 fencing token。一个跑了 40 秒的 agent 拿着过期的 30 秒租约回来写结果，板子不会拒绝它，因为它只校验 complete 时你手里有没有这张卡。这块要么靠任务本身的幂等，要么靠 worker 在收尾前先 renew 一次。

六、现在到哪一步#

Board 现在的身份是 experimental primitive，vercel board 是 CLI 的名字，也可以叫 vb。两个自家用例已经跑了，安全 agent 队伍和 v0 的 software factory。模板有两个，Factory 和 Swarm，一个是把人、agent、工具串成流水线，一个是把大工程拆成任务池并行。

原文那个演示页脚写着 scripted run，no models ran，人物和结果都是 illustrative。

我自己这一轮跑的是本地板，四张卡，两个 profile，零个模型。这四张卡上的事件和租约都是真的，包括那 29.6 秒。

八、自己验一遍#

不用注册，也不用登 Vercel，vb serve 就是一块本机板，数据落在当前目录的 .board/，默认地址 127.0.0.1:4100。

npx @vercel/board serve &
export BOARD_URL=http://127.0.0.1:4100/api/board

vb channels create work
vb tasks create work "Fix the flaky retry test" --label kind=bug --as codex
vb tasks claim 1 --lease 30s --as codex
time vb tasks claim 1 --as fx          # 预期 Can't claim task #1
sleep 31 && vb tasks claim 1 --as fx   # 预期拿到，lease 变成默认的 15m

30 秒之后同一张卡换人了，中间没有任何人去做判定死亡这个动作。计时用 time，冷启动的 node 会吃掉几百毫秒，别拿第一次的数字当常态。

九、路线图与开放问题#

  • 租约过期时活还没干完，哪一边负责让重做无害。任务内容里写清幂等的要求，还是让板子记一个 attempt 计数，两个都能做，代价不同。
  • 跨团队的两块板怎么合成一个视图。单板内的依赖现在是 needs，跨板的依赖没有看到入口，多团队协作最缺的恰好是这一格。

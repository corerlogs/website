AI 原生创业的四个阶段，和每个阶段的出口条件

把一份 36 页的创始人手册拆成能核对的部分：四个阶段各自的出口条件、AI 让哪几种失败变便宜了，以及手册没算的那笔账。数字都标了来源。

一句话　这份手册把创业讲成四道闸门，每个闸门配一个能回答是或否的问题。造东西变便宜之后，失败都挤到闸门这一侧。

同一个讲法在下面写成文字，插图与视频里的图是同一套。

一、先把手册的四道闸门摊开#

原文 36 页、7 章，骨架是四个阶段。每个阶段给一个出口条件，写成一个能回答是或否的问题，不是一个时间点。

阶段要回答的问题出口条件
Idea这件事值得做吗问题-方案匹配，证据主要来自真人对话
MVP先做哪一块一群具体的人愿意回来、付钱或者转告别人
Launch生意能不能长增长来自可重复的渠道，CAC、LTV、回收期是能报出来的数
Scale公司能不能离开你可持续的利润、IPO 条件、被收购，三者之一

手册把老路写成 validate、raise、hire、build、raise again、grow、hire more、repeat，主张今后每一段不必再换一批人、换一套技能、换一轮融资。第四章还给了这句话的落点，十人以下的公司可以按大公司的功能运转。

AI 在四段里省的东西不一样。Idea 省查资料和写文档的时间，MVP 省工程人力，Launch 省运维与合规的整理工作，Scale 省把公司知识变成流程的时间。这句是我按章节归纳的，原文没有这一句。

几个能核对的事实先摆在一起。

事实数字来源
手册篇幅36 页、7 章、4 个阶段原文实测
产品没人要导致的创业失败42%手册引用，原始为 CB Insights
Sean Ellis 判据40% 活跃用户答「非常失望」手册引用，行业惯例
Carta Healthcare 处理的手术病例每年 22,000 例，抽取时间下降 66%厂商案例
Anything 的用户数150 万厂商案例
手册给的访谈节奏每 5 场访谈归并一次证据手册建议，非数据

二、创始人的活被拆成三种工作面#

手册把工具写成三张桌子，区别在权限。同一个模型，工作区里装了什么，决定它能干什么。

任务用哪个面为什么
一句话改写、快速问答、读一段长 Slack 线程Chat快，不用配置
跨文件研究、从一文件夹访谈记录里出一份成稿Claude Cowork能读文件夹、连 Gmail 和 Calendar、按计划跑
写代码、跑测试、迁移、出 diffClaude Code代码库、git、本地或沙箱环境

这个划分有一个能检验的推论。把需要读文件夹的活丢给 Chat，人就得自己搬运上下文；把一句话改写丢给 Claude Code，多出来的步骤是等环境起来。选错面的成本不在能力，在搬运。

手册还给了一句判断，三个面底下是同一个 Claude，变的是外面的工作区。按这句话去读，Chat 和 Cowork 的边界会随连接器变，Claude Code 的边界由代码库和沙箱决定。

两份文档值得放在手边，一份讲 Claude Code 怎么工作 ，一份讲 CLAUDE.md 怎么配 。

三、Idea 阶段的出口是问题-方案匹配#

手册把问题-方案匹配拆成三个是或否。

  1. 问题是真实的、具体的吗。要能说出谁遇到它、多久遇到一次、影响多重、现在怎么对付。
  2. 你的方案解决的是不是那个问题。验证过程里冒出来的问题，和一开始假设的不一定是同一个。
  3. 有没有足够信号支持动手。这个阶段拿不到确定性，等确定性本身是一种失败模式。

「人们报销很痛苦」是观察。「中型公司的财务经理每周花 4 小时以上核对报销单，因为现有工具不接他们的会计软件」是可以测的假设。四小时这个数来自手册自己举的例子，我没有核过真实分布。

五个动作连起来是一条回路，每一步都得有产出。

动作产出什么时候算完
把假设改写到可测一句带人群、频率、严重程度、现有做法的描述四个要素都能填上
让 AI 站到反方一份反证清单，含失败竞品和结构性障碍反方论点比你的初稿硬
竞争地图分四层直接竞品、间接竞品、潜在收购方、可能切进来的邻居每层都写出它为什么是威胁
访谈问题先手写再送审问过去不问未来的一组问题没有「你会用吗」这类题
每五场访谈归并一次支持与反对两张清单两张都不空

让 AI 论证「某个竞品会赢而你不会」，比让它论证「你的差异化成立」有用，因为前者会去翻失败案例。手册把这个用法写成通用件，说它在每个阶段都能用。

访谈那一节的反面教材是这句，「你会用这样的东西吗」。该问的是「上一次遇到这个问题是什么时候」。前者得到的是想象，后者得到的是行为，还能顺手问到他们现在怎么凑合。

四、把原型当证据，是这一阶段最贵的错误#

手册引了一个旧数字，42% 的创业公司死于做了没人要的东西。这个数字来自 CB Insights 的失败原因统计，手册转引，原始样本的口径我没有找到。它至少说明这类失败在 AI 之前就排第一。

现在的问题是原型太便宜。agentic 编码把从有想法到有产品压到几个小时，流程就很容易变成有想法、马上做原型、拿原型当验证。原型在这里是压力测试道具，真人反应才是证据。手册给的剂量是五个人，从验证过的目标画像里挑。

第二个错误更隐蔽。让 AI 找支持你观点的证据，它找得到。让它估 TAM，它会给一个让你的市场看起来值得投的数。工具跟着你的方向走，一个不问硬问题的人能比以前更快地搭出一份看起来做过尽调的材料，并且全程觉得自己在尽调。解法是同一件工具朝反方向用，先让它找反证，再带着准备好的反驳去访谈。

第三个错误是提前规模化。agent 会用同样的热情去生成、测试、调试、重构一个前提错的代码库。手册的原话是系统里的智能是你的，这句要读两遍。

五、MVP 之前先写三份文档，再让 agent 写代码#

MVP 阶段容易被当成施工阶段。手册说它仍然是取证阶段，只是取证对象从问题换成方案。同一节还有一句更硬的话，怎么建决定了后面能做什么。

三份文档要在第一个功能之前写完。

文档回答什么不写会怎样
架构上下文 CLAUDE.md跟随哪些模式、避开哪些依赖、接受了哪些取舍每个会话从零推导结构，最后得到一个能跑但没有统一模型的代码库
范围文档产品做什么、明确不做什么、什么用户证据才配得上加东西每个小功能都便宜，产品慢慢越界，方向丢了也没人发现
度量框架留存基准、激活口径、D7 和 D30 的目标、假阳性长什么样上线之后才挑指标，挑的是能证明自己对的那几个

第二份文档里最有用的一列是「明确不做」。它把「要不要加这个」从争论改成查表，只有一批用户说缺了它拿不到价值时，才进范围。

技术债在 AI 项目里的机制和普通项目不同。普通技术债慢慢积累，能在一个专门 sprint 里还掉。会话式开发欠下的债会复利，因为没人把架构决定写下来，每个新会话重新推一遍，推出来的结论和上一个会话不一致，代码库于是没有统一的模型。单看每一块都不坏，合起来不是一起设计的。

手册给的维护剂量是每个会话五分钟。开始读一遍 CLAUDE.md 和范围文档，结束把这次的决定写回去，记下建了什么、改了什么、新引入了哪些假设。五分钟换的是一个你能讲清楚结构的代码库。

六、MVP 的三种假信号，和一件不能省的事#

早期动量是创业里最容易上瘾的体验。手册点了它的三个成分，朋友捧场、投资人别的被投公司里的意向买家、一条 Hacker News 标题带来的流量。这三样都不预测第六周和第十二周。

假信号长什么样一个能跑的检查
注册涨、激活不涨数字好看，用户没走到核心动作先把激活口径写下来，再看每一步的漏斗
有收入、没留存首月付费，第二个月不续按 cohort 看第二个月和第三个月
初期热情、没有回访launch 当天最热只看 D7 和 D30，不看当天

判据手册给了两个。Sean Ellis 的 40% 阈值问活跃用户「不能再使用这个产品会有多失望」，答「非常失望」的超过 40% 算一个 PMF 信号。另一个是力气测试。找到 PMF 之前，留存要靠人推，频繁触达、激励、创始人亲自跟进；找到之后，产品开始自己拉。推变成拉的那一刻比任何单一指标都可靠。

第三件事是安全。agent 生成的是能跑的代码，不是天生安全的代码。功能错了有反馈，漏洞没有反馈，一直到被利用才有。手册要求在任何真实用户碰到产品之前做一次安全审查，看四项，会话与鉴权、API 响应里的数据暴露、输入校验与注入、有已知漏洞的依赖。它同时提醒，Claude Code Security 当时是 limited beta。AI 扫描不能替代安全工具，在敏感数据和鉴权这条线上也不能替代人工复核。

七、Launch 阶段把创始人从循环里拿出来#

Launch 的出口有三条，缺一条就还在 MVP。

  1. 增长可重复，渠道清楚，CAC、LTV、回收期是你能报出来的数。
  2. 产品扛得住生产流量，安全和合规到位。
  3. 运维不经过你，支持、分流、sprint 计划、周报都有流程和自动化。

第三条最难，因为它是身份变化。MVP 阶段创始人在每个循环里是资产，Launch 阶段同一个习惯变成瓶颈。手册给了三个征兆，一小时能定的决定拖一周，只有你知道答案的支持请求堆起来，运营任务只在你想起来的时候才发生。

一个能直接跑的检查是「一周不在」测试。把每个工作流、决定、审批列出来，问它在你消失一周之后会怎样。会停下来的那些，说明交接标准、升级路径或者异常处理还没写清。

现在在你手上的事归类处理方式
每次发布前的检查清单能整个交出去写成脚本或流程，由 Claude Cowork 定时跑
支持请求里重复的那八成需要人，但不必是你先写分流树，再把常见问题写进文档
企业单的定价与承诺必须你只留这一格，其余排到它后面

合规在 Launch 变成产品工作流。SOC 2、GDPR、HIPAA 这些框架以前是融资到某轮才谈的事，现在客户数据一进来就适用。手册说把合规写进开发周期，不当成一次性项目，文档要持续维护。AI 扫描能帮你准备独立安全评估，不能替代有资质的合规审查。

八、Scale 阶段的护城河是三种时间锁定的积累#

Scale 的出口是阈值事件，可持续盈利、IPO 条件、被收购，三者之一。手册给了一个更锋利的问句，如果今天一个资金充裕的在位者抄了你的产品，用户会留下吗。

它认为护城河来自三种积累，共同点是都能用时间换，买不到。

资产怎么积累复制者要付什么
领域知识把行业黑话、监管坑、边角案例写成 skill 和上下文重新踩一遍你踩过的坑
用户行为数据记录哪些输出被接受、哪些被拒，接进模型改进等同样长的使用时间
工作流锁定集成、API、webhook、SDK，让用户在你上面搭东西一次完整的迁移项目

第一种的具体做法手册写得清楚。把「我怎么审一份商业租约」「我怎么分诊一张病人登记表」写成可复用的 routine，几十个月之后它会变成一层通用模型给不出的知识。第二种的关键在时间，用户在你产品里留下的行为指纹买不到，一个新来的复制者得从零等起。第三种是手册说的最深锁定，用户不只用你的产品，是在你上面搭东西，切换从产品决定变成一次运营项目。

企业单的门槛在另一处。多年度合同签之前，采购要看文档、SLA、可观测性、事故响应，这些是 Discord 社群支持阶段不需要建的东西。做 gap analysis 的办法是挑三个最难的潜在客户，问他们的采购团队会要什么，再照这份清单排技术工作和文档工作的顺序。

九、这套方法在哪失效，以及今天能跑的三个检查#

手册是厂商写的。每条建议最后都落到 Chat、Cowork、Code 三个面上，案例库里的六家公司都在用 Claude，没有一个失败案例，案例数字全部是厂商公布。这些不否定内容，但决定了它该怎么读，当操作清单用，别当证据用。

第二个失效点更具体。构建成本降了，验证成本没降。访谈一场要占一个人一小时，等用户回访要几周，付钱这件事没有捷径。四道闸门里有三道卡在真人和真钱上，所以「把季度压成周」在 Idea 和 MVP 阶段只对准备环节成立。

第三个失效点在组织。一个人创业的时候，三种工作面就是三个部门。二十个人的时候，谁有权改架构、谁能批一个范围变更、会话产物怎么进评审，手册没写。它假设的是极瘦团队，这个假设成立的地方它说的是真话，不成立的地方它没有备用方案。

三个今天就能跑的检查。

  1. 把范围文档补上「明确不做」和「什么证据才加」，回看过去一个月加的功能，数几条过了门槛。
  2. 做一周不在测试，把所有只有你能做的决定列出来，超过十条说明系统还没建起来。
  3. 找五个目标画像里的真人，只给他们一个核心交互，记下第一次卡住的位置。

两个我答不上的问题。构建成本接近零之后，验证成本为什么没有一起降；一个人加一群 agent 的组织，决策带宽的上限在多少人。

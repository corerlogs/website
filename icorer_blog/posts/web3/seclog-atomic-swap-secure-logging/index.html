SecLog 精读：把「数据已交付」写进链上，而不是把付款写进去

Posted by LB on Mon, Nov 2, 2026

一句话：要让「用户无法否认收到数据」成立，不需要信任 API、也不需要把数据放上链——只要让解密数据的最后一半钥匙，只可能从一条必然留下记录的路径里出现。

两分多钟的讲解片：钥匙怎么变成日志 → 两个事件的区别 → gas 那 8,000 的差额，以及我没复现出绝对值的部分。

论文是 SecLog: Atomic-Swap Based Secure Logging for Decentralized Data Sharing（Hughes、Hossain、Tang、Jung、Chenli；METAVERSE 2025，LNCS 16159，pp. 115–124）。它只有四页，但结构很干净：§1 交代问题，§2 把前人工作分两堆并介绍底座系统 Web3DB，§3 给模型、协议和两条定理，§4 用三个合约量 gas 并讨论代价，§5 收尾。下面按这个顺序走，标注每个主张在原文章节的位置，最后再放我们自己的复现结果。

一、问题：签完那份同意书之后，你就什么都不知道了

论文开头把场景写得很具体：数据每天都在产生，通常被某些中心方（公司、医院、数据中心）收集和共享；这些共享一方面改善了产品和研究，另一方面——生成数据的用户几乎不参与整个共享过程。原文的说法是：

“In many cases, the only thing that data generators … know about this process is when they initially sign the agreement for allowing some entity to share their data.” — §1

签完之后，数据所有者对共享的细节一无所知：谁访问了、什么时候访问的、数据被怎么用了。这不只是体验问题：没有透明度的共享，本身就与 HIPAA、GDPR、CCPA 这类法规不合规。

去中心化数据库（论文援引 recallnet 的 awesome-decentralized-database 列表）把所有权和控制权还给了数据所有者。但所有权回来之后，一个新的洞露出来：没有人负责记账。论文把它拆成三条具体的失败路径：

朴素做法为什么不行（论文 §1）
让用户自己确认收到「想否认收到数据的用户，不会向 API 确认」——确认这件事本身就没被强制
让 API 单方面写日志网络问题会让用户真的没收到，日志就写成假的；API 还成了单点故障（SPOF）
直接拿区块链存共享行为论文原话：cannot guarantee the correctness and the completeness of the logging——区块链保证的是不可篡改，不保证「该写的那一条一定被写」

第三条是要害。区块链擅长的事是「写上去的改不掉」，而这个场景缺的是「该写的一定会被写」。论文于是去公平交换（fair exchange）那条线找工具：那里用 HTLC 之类的原子交换，把「拿到数据访问权」和「付款」绑成一次要么全有要么全无的操作。SecLog 的洞察只有一句——把付款换成记录，原子性依然成立。因为在这个场景里，用户本来就不为取数付钱给 API；真正需要原子的是「拿到数据」与「某件事被触发」。

论文列了四条贡献：①一个原子交换式的记账协议，能在去中心化环境下强制「共享成功即留痕」；②给出了系统安全性证明；③仿真显示比付款型原子交换更省 gas；④代码开源（github.com/avocado-avery/SecLog，Apache/MIT 风格的短论文配套仓库）。

二、两条研究线走到哪儿了，以及底座是 Web3DB

论文的 §2 分三小节，正好对应下图的两列加一个底座：

§2.1 区块链日志这条线。 Gao 用同态加密保护链上审计日志，保密性上去了，代价是用户被排除在「验证自己被包含」之外；Cha 的 IoT 审计系统依赖可信基础设施；Zhao 与 López-Pimentel 把 Merkle 树哈希/根记到链上做防篡改，但明细留在链下，链下那份的可用性是个隐患；Hsu 把区块链和访问控制拼在 IoT 存储里；Cha 与 Hasan 用可信执行环境保护云日志；AuditChain、BlockAuditor、LogChain 采用了更去中心化的设计，但仍然假设基础设施里的参与者是诚实的，也不处理漏记（omission attack）。论文对这条线的总结值得抄下来：

“…the absence of mechanisms that allow users to independently confirm that their actions were successfully logged.” — §2.1

SecLog 的定位就是把「验证」塞进记账过程本身：enabling verifiable inclusion and censorship resistance without requiring trusted logger, storage node, or any single participant（同上）。

§2.2 公平交换这条线。 FairSwap、OptiSwap、Universal Atomic Swaps 用智能合约和密码学原语保证原子性；Zhu 与 Tas 把它推进到私钥交换与零知识证明。它们的共同边界是：为一次性交换设计——一笔币换一份数据或一个文件。论文的判断是 their models do not support persistent, auditable event streams：承载不了「每次查询都记一笔」这种持续事件流。

§2.3 底座 Web3DB。 这是 SecLog 挂载的系统：一个支持 SQL 的去中心化关系库，把控制权还给数据所有者。它分四层——数据注入层、访问控制层、数据库引擎层、数据存储层（底层用 IPFS）。

一次查询的路径是：用户把请求发给 SQL API；API 先找访问控制层，校验凭证、按 ACL 重写查询；再转给数据库引擎层，由一个随机选出的 master 节点协调其他 slave 节点执行；结果回到 API，API 再回给用户。论文在这里点出了 SecLog 要松掉的那颗螺丝：

“However, the underlying assumption behind this process is that the users are honest, i.e., they will not deny receiving the results.” — §3.1

在院内局域网里这个假设还算能用，放到公网就不成立了。

三、系统模型、安全模型与三条假设

SecLog 的 §3.1 把话说得很克制：只考虑三类实体——用户（发查询、等结果）、API（收请求、汇结果、回用户）、区块链节点（校验交易、执行合约）。区块链节点的作恶明确排除在范围之外：那属于共识机制领域，与本文无关。

安全模型只定义两条性质，都用一句话讲完：

  • 正确性（Definition 1）：链上任何一条共享记录，对应的共享确实完成了——API 发了查询结果，用户收到了数据。
  • 完整性（Definition 2）：任何一次成功的数据获取，链上都有对应记录。

这两条定义就是全文的靶子。三条假设则是它们的承重墙：

  1. 底层区块链安全且不被定向审查：无 51% 之类攻击，节点不串通去审查特定交易（用户的部署、API 的调用）；因此活性有保证——只要用户在 API 的调用被确认之后能连上一次网，就终将拿到数据。
  2. 查询结果加密传输：否则数据要么对链上所有节点可见，要么查询方可以否认收到。
  3. API 只会崩，不会骗：只考虑崩溃故障（最坏情况是对用户无响应），不考虑拜占庭故障；恶意数据提供方也不在范围内——数据正确性交给 Fair²Trade 那条线处理。

四、设计：四步、一个点、两个事件

§3.2 的四步可以照着图看：

  1. API 从引擎层取到结果后，用自己的密钥 sk 加密结果，再把 sk 随机拆成两半：sk = sk1 + sk2。这两步全在链下。

  2. API 把 sk1 和密文一起发给前端用户。到此为止，sk1 只有 API 和用户知道。

  3. 用户用 sk1 算出一个条件值，然后以它为条件部署合约。论文用的是 ElGamal 的例子：公钥 pk = g^sk，于是

    1cond = pk / g^sk1 = g^sk / g^sk1 = g^(sk − sk1) = g^sk2

    合约是一个变体的 HTLC：只有当 ecMul(sk2, G) == cond（即输入满足 g^input == cond）时，才触发并记录「收到回执」这个事件；否则事件不触发，合约到期作废。

  4. 部署之后，API 校验 cond 是不是它该给的那个点。是，就用 sk2 调用合约，触发记账事件；不是，就忽略这份合约。

输入验证这一步，论文明确说沿用了 Fair²Trade 的实现（ElGamal + 椭圆曲线乘），因为本文的贡献在「强制记账」而不在「输入验证」，篇幅所限没有展开完整的安全分析，请读者去看原文那位作者的设计。

合约本身只有 4.2 KB。读它有一个命名陷阱值得先说：字段叫 sk1x / sk1y，装的其实是 g^sk2 这个承诺点，不是 sk1。

1// contracts/SecLog.sol：sklockMatches 修饰器就是整篇论文的原子性
2(sk2x, sk2y) = EllipticCurve.ecMul(sk2, GX, GY, AA, PP);      // sk2 * G
3require(logs[_logId].sk1x == sk2x, "sk2 does not match");     // 与用户预置的点比对
4require(logs[_logId].sk1y == sk2y, "sk2 does not match");

1// contracts/SecLog.sol：只有 receiver（API）能触发，一次为限
2require(log.receiver == msg.sender, "Only receiver can verify");
3require(keccak256(_message) == log.messageHash, "Message hash mismatch");
4log.verified = true;
5emit LogVerified(_logId);

两个事件的分工就是整篇论文的骨架：

  • LogEntryNew（用户部署时发出）：logId、双方地址、承诺点、messageHash、时间锁。它证明的是意图。
  • LogVerified（API 调用 verifyLog 时发出）：只有点匹配、消息哈希匹配才会发生。它证明的是事实，同时把 sk2 永久写进 calldata。

五、安全分析：两条定理，各一段证明

§3.3 的写法很省：每条定理配一段证明。

定理 1（正确性）：只要用户在 API 的响应被区块链确认之后至少能访问一次链，协议就保证正确性。 证明：用户网络正常时，API 一给出正确的 sk2 就能恢复 sk。特殊情况是用户断开网络、不能及时看到链上更新；但按 §3.1 的假设，链的活性有保证——API 的输入被确认后，用户只要连上网络、收到一次更新，就能拿到 sk2 并取回结果。

定理 2（完整性）：只要 API 向用户部署的合法合约提供了合法输入，协议就保证完整性。 证明：与上一条同理。按 HTLC 的原子属性，正确输入被提供时，链上节点会验证并执行记账事件；因此只要合约部署正确，合法输入总会触发事件，记录必然上链。

两个证明都成立，而且都短——因为它们做的事情是把模型已经给出的东西命名清楚。真正的工作量在 §3.1 那三条假设里：活性、加密传输、API 不撒谎。这也是我们读这篇论文时最想说的一句：这份设计的安全性，是「用一条链的活性」换来的；它把信任从一个API挪到了一整条链上，而不是消灭了信任。

六、评估：三个合约，一张图，和我们的重跑

§4.1 的实验设置：以太坊智能合约，Truffle + 本地 Ganache，Solidity 0.5.0，gas 直接从 Ganache 日志和 Truffle 控制台采集。比较三个合约：

  • SecLog.sol：本文方案。
  • Fair2Trade.sol：付款型原子交换的基准。在 Fair²Trade 里，数据买方建 HTLC，数据中间方（broker）交出数据访问权来换取押金。
  • CIDLog.sol：论文自造的天真基准。不加密结果，而是把结果存进 IPFS，拿结果的 CID 当 sk 去和用户做 HTLC 交换。

结论是：SecLog 比 Fair²Trade 少约 8,000 gas。原因是 Fair²Trade 在 broker 交出合法 sk2 之后要发起一笔押金转账，而 SecLog 只触发一个「确认收到合法输入」的事件。差额小于一次 ETH 转账的 21,000 gas，因为 SecLog 多了一个确认操作也要花 gas。CIDLog 的 gas 与 SecLog 相同——CID 和 sk 都是 32 字节，验证成本一样；但 CIDLog 的用户在原子交换完成前下载不了数据，还多引入一个 IPFS 实体，验证难度更高。

我把同一份字节码搬到一个本地 EVM 上重跑（solc 0.5.17，py-evm 的 Istanbul 与 London 两个分叉），结果一半对上一半对不上：

  • 相对结论复现了：Fair2Trade − SecLog = 8,038 gas（London）/ 8,026 gas（Istanbul）。论文正文说 8,000，作者仓库里的图表数据是 8,166（696,991 − 688,825）。误差 1.6%。
  • 绝对值没复现：论文 Fig.2 是 688,825 gas，我同一份字节码跑出 186,415 gas，差 3.7 倍。我怀疑过 EVM 分叉：Berlin 前后的 modexp 计价差得很多，而这条曲线的库正是靠 modexp 做模逆。但 Istanbul 分叉下也才 179,327，仍然差得远，所以这个解释不成立。短文的数字是 Truffle + Ganache 采集的，栈不同——这类论文的 gas 绝对值不能横向比较，能跨栈复用的只有差额和量级。

除了这条对比，论文还留了一个能自己算的锚：按 Etherscan gas tracker（2025-07-26），一次执行约 $0.75。用同一 gas 价折算，我们复现的 186,415 gas 约 $0.20，而用户的部署费（1,164,022 gas）约 $1.27。

七、讨论：论文自己承认的三种开销

§4.2 是全文最诚实的一节，它列了三类新增成本，并且没有粉饰：

  1. 网络负担：用户必须和区块链交互才能收到 API 的输入，这对用户的网络质量提出了额外要求；而且同步频率取决于底层链——比特币出块约 10 分钟，以太坊约 12 秒。
  2. 链的维护成本：论文把活性当成假设，但没把维护链的费用算进协议账里；具体选哪条链由实现决定，维护成本随之变化。
  3. 链下开销：数据加解密、密钥拆分。论文给的数量级是：AES 加密 1 MB 载荷 不到 10 ms，密钥拆分 1 ms 以内，与链上开销相比都很小。

把这三条和第六节的 gas 放在同一个尺子上，就成了下面这张图——左边是时间，右边是钱：

这张图读出来的结论比论文正文更刺：密码学比起共识几乎免费。这条协议的花费不花在椭圆曲线上，而花在「等一个块」和「付一笔 gas」上。所以论文说「比付款型交换便宜 8,000 gas」是对的，但那只是链上账单里的一小格；真正的账是「一次交换要付 116 万 gas 的部署费」。

九、你可以自己验证的三件事，以及论文留下的两个问题

三条命令都只依赖公开数据，不需要跑链：

 1# 1. 原子性的那一行：合约里到底比对了什么
 2curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 3  | grep -n "ecMul\|keccak256(_message)\|emit LogVerified"
 4
 5# 2. 查询内容是不是明文上链：看 verifyLog 的参数
 6curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 7  | grep -n "function verifyLog" -A 3
 8
 9# 3. 成本换算：从「688,825 gas 约 $0.75」反推隐含 gas 价，再看复现的 gas 值多少
10python3 -c "p=0.75/688825; print(round(p*1e9,3),'gwei-equivalent'); print('186,415 gas ->', round(186415*p,2), 'USD')"

第 2 条是关键：verifyLog(logId, sk2, message) 里的 message 必须是明文，否则 keccak256(_message) 对不上 messageHash。也就是说，这套设计默认查询内容会随记录一起公开。想同时要隐私，就得把 messageHash 换成承诺（比如哈希的哈希），但那样合约就校验不了内容了——这是一个二选一，论文没有选。

论文留下的两个问题：

  • 谁付这笔账？ 论文只比较了「验证」这一步。把一次交换的总账算完：用户先付约 116 万 gas 部署，API 再付约 18.6 万 gas 验证，而朴素的「API 记一条日志」只需要一次 SSTORE 加一个事件。省下的 8,000 gas 换来的是不信任 API；这个信任缺口在多少场景里值 100 万 gas，论文没回答。
  • 能不能聚合？ 每个查询一笔交易，1 万次查询就是 1 万笔。作者另一条 Fair²Trade 的线用 epoch + Merkle 根摊销（他们 repo 里的 Chart.ipynb 就在算这个），SecLog 这篇没做：把一个椭圆曲线承诺换成一棵 Merkle 树，原子性还在吗？

这两个问题我答不上来。第二个我认为是这篇论文最明显的下一站。

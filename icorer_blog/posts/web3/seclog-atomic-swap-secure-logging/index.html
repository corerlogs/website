SecLog：把「数据已交付」写进链上，而不是把付款写进去

Posted by LB on Mon, Nov 2, 2026

一句话：要让「用户无法否认收到数据」成立，不需要信任 API、也不需要把数据放上链——只要让解密数据的最后一半钥匙，只可能从一条必然留下记录的路径里出现。

两分半的讲解片：钥匙怎么变成日志 → 两个事件的区别 → gas 那 8,000 的差额，以及我没复现出绝对值的部分。

一、问题：签完协议之后，你就什么都不知道了

集中式数据共享里，数据生成者签署一次同意书，之后整个链条对他关闭。美国医院协会（AHA）健康创新中心的报告写得很直白：医疗行业正在用数据改善患者体验、成本和临床绩效——而生成这些数据的病人在共享流程里几乎不参与。谁在什么时候、用什么条件读了你的记录，你无从得知。这不只是体验问题：HIPAA、GDPR、CCPA 都要求可追溯，而「不可追溯」是这些系统合规不了的第一道坎。

去中心化共享系统（Web3DB、OrbitDB、IceFireDB 这一类）把所有权还给了数据生成者：查询照旧打到 SQL API，访问控制层校验凭证、重写查询，存储层落在 IPFS 上。但所有权回来之后，一个新的洞露了出来——没有人负责记账。

  • 让用户自己确认收到数据？想赖账的用户不会确认。
  • 让 API 单方面写日志？网络抖动时用户确实可能没收到数据，那日志就写成了假的；而且 API 成了单点故障，也成了唯一可信方。

所以真正的要求不是「记日志」，而是交付与记录必须原子：要么两件事同时发生，要么都不发生。这个性质在公平交换（fair exchange）里被研究了十几年，而那里原子性交换的是「数据访问权」和「付款」——SecLog 的洞察是，把付款换成日志，原子性依然成立。

二、业界到哪一步了

论文把前人工作分成两堆，各自的缺口正好互补：

主张后果
AuditChain、LogChain、BlockAuditor 用区块链存日志，防篡改仍假设基础设施诚实，不防漏记（omission attack）；前端无法自证「我这次操作被记下了」
Merkle 根/哈希上链、明细留在链下可验证性只到批次层；链下那份明细的可用性没人担保
FairSwap、OptiSwap、Universal Atomic Swap、Fair²Trade、Tas 等用智能合约保证原子为一次性交换设计：一笔币换一份数据或一个文件，不是持续的事件流，无法承载「每次查询都记一笔」
Web3DB 把 RDBMS 拆成注入/访问控制/引擎/存储四层，控制权回到 owner交付阶段依赖「用户是诚实的」这一假设：用户不会否认收到结果

缺口的形状很清楚：要的是「前端用户能独立确认自己的行为被记下了」，而既有工作要么把信任放在基础设施上，要么只对一次性交换成立。SecLog 的定位就是补上这一格。

三、设计：把要求写成要件，方案就只剩一个

论文把两条定理写成了定义，我把它反过来当作设计要件：

  1. 正确性：链上出现的每一条共享记录，都对应一次真的完成了的共享。
  2. 完整性：每一次成功的数据获取，链上都会留下对应记录。
  3. 不把数据放上链：链上只留最小事实（一个椭圆曲线点 + 一个哈希）。
  4. 到期能作废：没有完成交换的那一侧不能留下假记录。

由此推出两条原则：

  • 最后一半钥匙只在链上出现：谁想解密，就必须走一条会留下痕迹的路。
  • 链上写的是「这场交换发生了」，不是「这场交换的内容」。

实现方式借自 Fair²Trade 的 ElGamal 变体 HTLC，把「付款」这一动作换成「记账」。API 的密钥 sk 决定公钥 pk = g^sk，加密查询结果后把 sk 随机拆成 sk = sk1 + sk2，先把 sk1 连同密文交给用户（链下）。用户算出承诺点：

1cond = pk / g^sk1 = g^sk / g^sk1 = g^(sk - sk1) = g^sk2

然后以 cond 为条件部署日志合约。API 想交付数据，就必须把 sk2 交给合约；sk2 一旦上链，任何人（包括用户）都能算出 sk = sk1 + sk2 并解密——交付完成和记录上链成了同一件事。

四、实现：合约里只有两个事件值得看

仓库里的 SecLog.sol 一共 4.2 KB，核心是三段 require 加两个 emit。理解它的捷径是先看懂一个命名陷阱：合约里字段叫 sk1x / sk1y，装的却是 g^sk2 这个点（用户提交的承诺），不是 sk1 本身。

1// contracts/SecLog.sol：sklockMatches 修饰器就是整篇论文的原子性
2(sk2x, sk2y) = EllipticCurve.ecMul(sk2, GX, GY, AA, PP);      // sk2 * G
3require(logs[_logId].sk1x == sk2x, "sk2 does not match");     // 与用户预置的点比对
4require(logs[_logId].sk1y == sk2y, "sk2 does not match");

1// contracts/SecLog.sol：只有 receiver（API）能触发，一次为限
2require(log.receiver == msg.sender, "Only receiver can verify");
3require(keccak256(_message) == log.messageHash, "Message hash mismatch");
4log.verified = true;
5emit LogVerified(_logId);

两个事件的分工是整篇论文的骨架：

  • LogEntryNew（用户部署时发出）：记录 logId、双方地址、承诺点、messageHash、时间锁。它证明的是意图。
  • LogVerified（API 调用 verifyLog 时发出）：只有 ecMul(sk2, G) == cond 且 message 哈希匹配才会发生。它证明的是事实，同时把 sk2 永久写进 calldata。

五、取舍与代价

决策备选理由代价
触发事件（emit）而不是转账Fair²Trade 的 receiver.transfer(amount)场景里没有付款，只有交付复现中省了约 8,000 gas，但谁付 gas 变了：用户付部署费，API 付每次验证费
message 以 calldata 公开只上哈希、或上零知识证明合约要校验内容，就必须看见内容查询内容对全网公开；隐私只能靠外层另做（论文未讨论）
用户先部署合约API 先承诺、用户后验证让「想赖账的一方」先出钱，抑制女巫式撒网用户先垫 116 万 gas 的部署费（复现值），兑换一笔才发现值不值
复用 ElGamal 输入验证自研验证协议Fair²Trade 的实现已验证过，省掉安全论证复杂度与 gas 全押在椭圆曲线上：单次调用约四分之三是 ecMul
记录绑定 messageHash不绑定一条记录能对应一次具体查询想让记录可核验，就把查询公开了

六、现在到哪一步：相对结论成立，绝对数字没复现出来

论文是一篇 4 页的 short paper：一个协议、两条定理（都依赖「区块链有活性、不审查特定交易」这一假设）、三个合约的 gas 对比、开源代码。定理的证明是「如果用户能联网一次，就能拿到 sk2」——这在模型内成立，但它把最难的部分（活性）留在了假设里。

我按它仓库里的合约原样搬到一个本地 EVM 上重跑了一遍（solc 0.5.17，py-evm 的 Istanbul 与 London 两个分叉）：

  • 相对结论复现了：Fair2Trade − SecLog = 8,038 gas（London）/ 8,026 gas（Istanbul），论文说 8,000，作者 repo 的图表数据是 8,166。误差 1.6%。
  • 绝对值没复现：论文 Fig.2 是 688,825 gas，我同一份字节码跑出 186,415 gas，差 3.7 倍。我没有找到能解释这个差异的 EVM 分叉（Berlin 前后的 modexp 计价差异我试过，Istanbul 下是 179,327，仍然差得远）。

这件事对读者的意义不在于「论文错了」——短文的数字是 Truffle + Ganache 采集的，栈不同；而在于这类论文的 gas 数字不能横向比较，能用的是差额和量级。差额是稳的，因为在两套栈里它都由同一件事决定：省掉一次转账（21,000 gas）换成一个事件。

八、你可以自己验证的三件事

三条命令都只依赖公开数据，不需要跑链：

 1# 1. 原子性的那一行：合约里到底比对了什么
 2curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 3  | grep -n "ecMul\|keccak256(_message)\|emit LogVerified"
 4
 5# 2. 查询内容是不是明文上链：看 verifyLog 的参数
 6curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 7  | grep -n "function verifyLog" -A 3
 8
 9# 3. 成本换算：从「688,825 gas 约 $0.75」反推隐含 gas 价，再看复现的 gas 值多少
10python3 -c "p=0.75/688825; print(round(p*1e9,3),'gwei-equivalent'); print('186,415 gas ->', round(186415*p,2), 'USD')"

第 2 条是关键：verifyLog(logId, sk2, message) 里的 message 必须是明文，否则 keccak256(_message) 对不上 messageHash。也就是说，这套设计默认查询内容会随记录一起公开。想同时要隐私，就得把 messageHash 换成承诺（比如哈希的哈希），但那样合约就没法校验内容了——这是一个二选一，论文没有选。

九、路线图与开放问题

  • 谁付这笔账？ 论文只比较了「验证」这一步：SecLog 比 Fair²Trade 便宜 8,000 gas。但把一次交换的总账算完，用户要先付 116 万 gas 部署，API 再付 18.6 万 gas 验证。相比「API 记日志」的朴素方案（一次 SSTORE 加一个事件），这套协议贵了两个数量级。省下的 8,000 gas 换来的是不信任 API；问题是：这个信任缺口在多少场景里值 100 万 gas？
  • 能不能聚合？ 每个查询一笔交易，1 万次查询就是 1 万笔。作者另一条 Fair²Trade 的线用了 epoch + Merkle 根摊销（他们 repo 里的 Chart.ipynb 就在算这个），SecLog 这篇没有做：把一个椭圆曲线承诺换成一棵 Merkle 树，原子性还在吗？

这两个问题我答不上来。第二个我认为是这篇论文最明显的下一站。

SecLog: log the data handover, not the payment

Posted by LB on Mon, Nov 2, 2026
中文版是这篇文章的默认版本。 阅读中文版 →
This English page stays available at this URL; the Chinese version is the one we maintain first.

In one line: “the user cannot deny receiving the data” needs no trusted API and no data on chain — only a design where the last half of the decryption key can appear through one path, and that path leaves a record.

Just over two minutes: how a key becomes a log entry → the two events and what each one proves → the 8,000-gas gap, and why I could not reproduce the absolute number.

1. The problem, as a scene

You sign one consent form, and the chain closes behind you. The American Hospital Association’s Center for Health Innovation says the industry already uses data to improve patient experience, cost and clinical performance — while the patients who generate that data take almost no part in the sharing. Who read your record, when, under which condition: unknowable. That is not a UX complaint. HIPAA, GDPR and CCPA all require traceability, and “not traceable” is the first wall such a system hits.

Decentralized sharing systems (Web3DB, OrbitDB, IceFireDB and friends) hand ownership back: queries still go to a SQL API, an access-control layer validates credentials and rewrites the query, storage sits on IPFS. Ownership returns — and a hole opens where a trusted party used to be: nobody keeps the record.

  • Ask the user to confirm receipt? A user who wants to deny it simply does not.
  • Let the API write the log unilaterally? A flaky network can mean the user genuinely never received the payload, so the API writes a false entry; and the API becomes both a single point of failure and the one party you must trust.

So the requirement is not “keep a log”. It is the handover and the record must be atomic — both or neither. Fair exchange has studied exactly this property for a decade, atomically trading access to data for payment. SecLog’s move is to swap the payment for the record: atomicity survives.

2. Where the research stands

The paper splits prior work into two piles whose gaps complement each other:

ClaimConsequence
AuditChain, LogChain, BlockAuditor store logs on chain, tamper-evidentStill assume an honest infrastructure and do not stop omission: the front-end user cannot prove that their action was logged
Merkle roots and hashes on chain, detail off chainVerifiability stops at the batch level; nobody guarantees the off-chain detail survives
FairSwap, OptiSwap, Universal Atomic Swap, Fair²Trade, Tas et al. enforce atomicity with contractsBuilt for a single-shot exchange — coins for a file — not for a continuous event stream where every query must be logged
Web3DB splits an RDBMS into injection / access control / engine / storage layers, control back to the ownerThe delivery step still assumes the user is honest: they will not deny receipt

The gap has a specific shape: the front-end user needs to confirm independently that their action is on the record, and existing work either trusts the infrastructure or only holds for one-shot trades. That cell is what SecLog fills.

3. The design

Read the paper’s two theorems backwards and they become requirements:

  1. Correctness — every sharing record on chain corresponds to a sharing that actually happened.
  2. Completeness — every successful retrieval leaves a record on chain.
  3. No data on chain — only a minimal fact: one elliptic-curve point and one hash.
  4. Expiry leaves nothing — the side that did not complete the exchange cannot leave a fake entry.

Two principles fall out:

  • The last half of the key exists only on chain. Anyone who wants the plaintext must take a path that leaves a trace.
  • The chain records that an exchange happened, not what it was.

The mechanism borrows Fair²Trade’s ElGamal-flavoured HTLC and swaps the payment action for a logging action. The API’s secret sk defines pk = g^sk; it encrypts the query result, splits the key at random (sk = sk1 + sk2), and sends sk1 with the ciphertext off-chain. The user computes a commitment point:

1cond = pk / g^sk1 = g^sk / g^sk1 = g^(sk - sk1) = g^sk2

and deploys a log contract carrying cond as its condition. To deliver, the API must hand sk2 to that contract; once sk2 is on chain, anyone — the user included — computes sk = sk1 + sk2 and decrypts. Delivery and record become one act.

4. The implementation

SecLog.sol is 4.2 KB: three requires and two emits. The shortcut to reading it is a naming trap — the struct fields are called sk1x / sk1y but hold the point g^sk2, the user’s commitment, not sk1 itself.

1// contracts/SecLog.sol: sklockMatches is the whole paper's atomicity
2(sk2x, sk2y) = EllipticCurve.ecMul(sk2, GX, GY, AA, PP);      // sk2 * G
3require(logs[_logId].sk1x == sk2x, "sk2 does not match");     // compare with the user's point
4require(logs[_logId].sk1y == sk2y, "sk2 does not match");

1// contracts/SecLog.sol: only the receiver (the API) may trigger it, and only once
2require(log.receiver == msg.sender, "Only receiver can verify");
3require(keccak256(_message) == log.messageHash, "Message hash mismatch");
4log.verified = true;
5emit LogVerified(_logId);

The two events are the skeleton of the paper:

  • LogEntryNew (emitted when the user deploys): logId, both addresses, the commitment point, messageHash, timelock. It proves intent.
  • LogVerified (emitted when the API calls verifyLog): only fires if ecMul(sk2, G) == cond and the message hash matches. It proves fact, and it permanently writes sk2 into calldata.

6. Where it stands

The paper is a four-page short paper: one protocol, two theorems (both resting on the assumption that the chain is live and does not censor specific transactions), a gas comparison across three contracts, and open code. The proofs reduce to “if the user can get online once, they can get sk2” — true inside the model, with the hard part (liveness) left as an assumption.

I took the contracts from the authors’ repository as-is onto a local EVM (solc 0.5.17, py-evm, Istanbul and London forks):

  • The relative claim reproduces: Fair2Trade − SecLog = 8,038 gas (London) / 8,026 gas (Istanbul). The paper says 8,000; the authors’ chart data says 8,166. Within 1.6%.
  • The absolute number does not: the paper’s Fig. 2 reports 688,825 gas; the same bytecode costs 186,415 gas here — a 3.7× gap. I could not attribute it to an EVM fork either: the Berlin-era modexp repricing was my first suspect, but Istanbul gives 179,327, still far off.

The useful takeaway is not “the paper is wrong” — a short paper measured on Truffle + Ganache, a different stack — it is that gas numbers in this literature cannot be compared across papers. What travels is the delta and the order of magnitude, and the delta is stable because both stacks are measuring the same one thing: one value transfer (21,000 gas) removed, one event put in its place.

8. What you can check yourself

Three commands, all against public data, no chain required:

 1# 1. the atomicity line: what the contract actually compares
 2curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 3  | grep -n "ecMul\|keccak256(_message)\|emit LogVerified"
 4
 5# 2. is the query public? look at verifyLog's parameters
 6curl -s https://raw.githubusercontent.com/avocado-avery/SecLog/main/contracts/SecLog.sol \
 7  | grep -n "function verifyLog" -A 3
 8
 9# 3. cost: back out the implied gas price from "688,825 gas ≈ $0.75", then price the rerun
10python3 -c "p=0.75/688825; print(round(p*1e9,3),'gwei-equivalent'); print('186,415 gas ->', round(186415*p,2), 'USD')"

The second one is the load-bearing check: verifyLog(logId, sk2, message) needs message in the clear, otherwise keccak256(_message) cannot match messageHash. In other words, the design assumes the query is published alongside the record. Keep privacy and you must replace messageHash with a commitment (a hash of a hash) — and then the contract can no longer check the content. That is a fork in the road the paper does not take.

9. Roadmap and open questions

  • Who pays the bill? The paper compares only the verification step: SecLog is 8,000 gas cheaper than Fair²Trade. Total the exchange and the user pays ~1.16M gas to deploy, the API pays ~186k to verify. Against the naive alternative — the API writes one SSTORE and emits one event — this protocol is two orders of magnitude more expensive. What the 8,000 gas buys is not trusting the API. So: in how many settings is that trust gap worth a million gas?
  • Can it aggregate? One transaction per query means 10,000 transactions for 10,000 queries. The authors’ other Fair²Trade line amortises with epoch + Merkle roots (their Chart.ipynb is literally about this); SecLog does not. Replace the single curve commitment with a Merkle tree — does atomicity survive?

I cannot answer either. The second one looks like the obvious next paper.

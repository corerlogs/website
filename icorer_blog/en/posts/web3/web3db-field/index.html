The Bytes Moved, the Compute Didn't: A Field Report on Web3 Databases, via Web3DB

The decentralized-database field has not been losing on consensus strength. It has been losing because compute never followed the bytes. Web3DB states the bill: 22 TPC-H queries, 18 nodes, 2.85x, 15.8% parallel efficiency — and six routes that each bought exactly one layer.

In one line: the field’s unsolved problem is not that consensus is too weak, it is that compute never followed the bytes. Web3DB is one of the few papers that prices this out loud: 22 TPC-H queries, 18 nodes, 2.85x speedup, 15.8% parallel efficiency, plus an explicit admission that it chooses CA and will not survive a partition.

1. The problem, as a scene#

In 2016 “blockchain database” was a term of art. BigchainDB gave the plainest answer on offer: MongoDB stores, Tendermint orders, every node keeps a full copy, a write is final the moment it lands. It collected 4,030 stars and a place in every survey’s comparison table.

The GitHub record says the last push was 2024-07-04 and the last release, v2.2.2, was September 2020; the successor work went to Planetmint under the IPDB Foundation. It is still the sample a reviewer reaches for when asked what a decentralized database looks like.

It is not alone. Kwil sold its decentralized stack to TRUF.NETWORK in April 2025, which open-sourced it; Tableland raised an $8M Series A led by CoinFund in April 2023 and has $10.4M in total; Space and Time went to mainnet in May 2025 betting the whole story on zero-knowledge proofs of query results; OrbitDB spent a decade reaching v3 in August 2025 and shipped a v4 release candidate in April 2026.

The field’s obituary list is about as long as its product list, and the deaths share one shape: each project decentralized exactly one of four layers and then claimed the whole database was decentralized.

2. Where the field stands: who actually bought which layer#

A database is not one object. It is four: write order, byte location, execution location, read permission. Split them apart and every argument in this field collapses into the same multiple-choice question — which layer are you paying to decentralize?

None of those six rows is wrong: the ledger puts write order on a chain, P2P turns replica sync into a protocol, Tableland puts table names and permits on-chain, Space and Time turns “is the answer right” into a proof, IPFS only knows where the bytes are, and Web3DB moves both permission and master election. None of them stands alone either. That is why “where is the Web3 database field today” has exactly one honest answer: which of the four layers do you mean?

One note on our own product. The column where the paper marks IceFire DB with an ✗ is “full support of relational SQL”, and the mark is fair: IceFireDB’s SQL side is SQLite with CRDT replication plus a MySQL-protocol proxy, with no cross-node JOIN and no query pushdown. But the row is worth a pause, because it shows the field’s path dependence exactly. Projects that grew out of the IPFS ecosystem got KV and CRDT; out of the blockchain ecosystem, a ledger; out of Postgres (Kwil), SQL with consensus swapped in; out of a research group (Web3DB), Spark and Hive. Nobody designed four layers at once. Everyone grew upward from the one layer they already had.

The most recent rename follows the same logic. Golem DB became Arkiv in 2026: an L2 on Ethereum with several L3 “database chains” under it, billed by how long data is retained. It no longer calls itself a database. It calls itself a data availability layer — the same move, one layer up, with a new name.

3. The design, stated as requirements#

Read the paper as requirements and there are only four:

  1. Keep the relational model and SQL. Not aesthetics — compatibility. The legacy systems, the BI tools and the people who know SQL all live there.
  2. Permissions must be verifiable, revocable and row-level. The smallest enforceable unit of data sovereignty is not a file, it is one row of one table.
  3. Multi-tenancy. One table serves several data owners, and each sees only its own rows.
  4. Decentralized execution. No permanent master, no node that always knows everything.

Two principles carry those requirements, and the second one matters more than it looks:

  • P1, pluggable layers. Any single layer can be decentralized independently. The paper’s words: “selectively decentralize any layer/component of their choice”, so different use cases can buy different trade-offs.
  • P2, a stateless master. The master is drawn by lot, holds nothing but a private key, and is thrown away after one query.

P1 is the most valuable sentence in the paper because it turns decentralization from a boolean into a configurable quantity. Every tragedy in section 2 is a project that sold the boolean.

4. The implementation, layer by layer#

Data Injection. A JavaScript front end talks to MetaMask so the user’s key never leaves the wallet; a C# API sits behind it. This is the one layer still centralized, which the paper admits in its future work.

Access Control. Hyperledger Fabric and smart contracts. The ACL holds three things per user: the public key, hashes of the data they own, and hashes of the data they may read. A query sends the user’s public key and the target tables on-chain; the contract checks the ACL and returns the data hash to the execution layer.

There is a detail the paper does not develop: identity lives on Ethereum, permissions live on Fabric. Two trust roots, two chains, two consensus mechanisms, and no specification of the bridge between them. In a prototype that is a footnote. In production it is the first thing anyone attacks.

Database Engine. Spark and Hive on a gossip network (Boost.ASIO). A query is broadcast, each node runs a VRF sortition — Algorand’s Algorithm 1/2 with the weights changed and the role parameter removed — and the number of sub-slots a node wins is read off where its hash falls in a binomial distribution. The outputs go back on-chain, the chain waits a fixed interval to collect them, and BA⋆ converges on who is master for this round.

The master then does three things: encrypt the result back, set every worker’s weight to 1, set its own weight to 0, and clear its cache through Spark:

// engine: after the query, the master unpersists the RDDs it cached
rdd.unpersist(blocking = true)

Data Storage. Public IPFS. Every engine node also runs an IPFS daemon; a table update is written back to IPFS and the new hash returns to the ACL.

The expensive part is not consensus. It is materialization. Section VI says it plainly: transfer between the engine and IPFS significantly lengthens execution, because queries cannot run directly on IPFS’s CAR format — an open problem.

In plain terms: content-addressed storage sells a database the location of bytes, but a database needs compute moved next to the bytes. Web3 spent ten years on the first half and none on the second.

6. Where it stands#

Section V-B contains an unusually honest sentence: trying to scale to 20 nodes, “the network was crashing every time on AWS”.

Averaging Table III’s 22 queries at each node count produces three things the paper does not spell out:

  1. Two nodes buys 1.06x. The first increment is almost entirely eaten by coordination.
  2. Eighteen nodes buys 2.85x, with 15.8% parallel efficiency.
  3. Marginal return per added node: 0.14x per node going 5 to 10, then 0.065x per node going 10 to 18 — it halves once.

The third point is the one that should not be skipped: the curve is not “add machines until it is fast”. It is already bending.

The authors hide nothing: no partition tolerance, a crash at 20 nodes, an explicit assumption that database engines do not go offline. That kind of honesty is rare in systems papers.

The more informative signal is outside the paper. web3db.org now leads with TEEs and ZKP, not with the on-chain ACL, and the project page under LF Decentralized Trust Labs is marked archived. The direction moved: from consensus enforcing permissions to hardware enforcing them.

Every row is computed from the 22 raw rows of Table III: mean latency is the arithmetic mean, speedup is the 1-node mean over the N-node mean, efficiency is speedup divided by node count.

Three things to check:

  • The prose claims a 20% improvement at three nodes, but Table III has columns for 1, 2, 5, 10 and 18 only. That number has no row.
  • “Improvement” here means reduced latency, not speedup. 64% less time is the same measurement as 2.85x, and readers remember the better-sounding one.
  • The 22 queries ran sequentially. This measures single-query latency, not throughput — the paper does not say so, but the shape of Table III does.

The dataset is TPC-H at scale factor 10, roughly 10 GB, on EC2 instances spread across eight regions (us-east-1/2, us-west-2, eu-west-2/3, eu-central-1, ap-south-1, ap-northeast-2, ap-southeast-1). Cross-region RTT is inside the execution times and is never broken out as its own cost.

8. What this buys you#

If you are deciding whether to put a project on a Web3 database, this four-question flow is worth more than any feature matrix:

One check you can run today: measure the materialization share of your target query on CAR. If fetching and deserializing blocks is more than 30% of wall time, your bottleneck is I/O, and no consensus algorithm will fix it.

Keep the counter-example. Three cases make the cost worth paying:

  • append-only, rarely point-queried data — audit logs, compliance archives;
  • data shared across parties where no single party should hold the full plaintext — health, credit, supply chain;
  • authorization records that must be non-repudiable — who let whom read which row, verifiable by a third party.

Web3DB’s medical scenario lands in the last two, which is exactly why it attracted NSF money. It also shows the bill: to make “who may read this” verifiable, you pay with “how fast can it be read”.

9. Roadmap and open questions#

The paper’s future work has three items: decentralize the API layer, strengthen encryption, improve partition tolerance without giving up consistency. The first two are engineering. The third is research.

Two questions nobody can answer yet:

  • If the master must see plaintext, whose trust root is higher — the TEE’s or the chain’s? The site’s pivot to TEE says the team picked hardware. But “prove with hardware that the software behaved” and “prove with consensus that nobody can rewrite the record” are different kinds of trust, and selling them as one thing will eventually break.
  • Can content-addressed storage carry a verifiable index? No index means no pushdown; no pushdown means no database. Whoever makes an index that is verifiable, incrementally maintainable, and addressable alongside its blocks will actually have solved this field’s problem — instead of shipping another decentralized database.

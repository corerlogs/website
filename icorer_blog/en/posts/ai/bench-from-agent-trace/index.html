Build One Task Before You Build a Benchmark

Skip the leaderboard. Your own agent traces already hold terminal-grade eval tasks. Find, cut, rebuild the environment, run, read the trace. Five moves turn one real failure into a benchmark task.

A benchmark score is an average over a few dozen tasks, and that is the most it can be. What is scarce is whether the gap inside one of those tasks is still there.

1. The gap lives in your own session#

James Zhu published 大bench时代生存指南 on X on 27 November, and this is the route it lays out. He runs Benchmarks’ Last Exam, which spends its days taking other people’s tasks apart. He opens with one piece of advice. A single high-quality task is worth more than the benchmark you were about to start.

You hand an agent real work, it makes a mess of your workspace, you correct it turn by turn, and somewhere near round one hundred it produces something usable. For you the session is over. For whoever writes tasks, it has just started.

A session like that mixes several kinds of failure, and they have to be separated before any of them becomes a task.

Why it failedWhat it looks like in the traceCan it be a task
The context was incompleteThe key constraint arrives from you at turn fiftyNo, writing it into the prompt removes it
The capability was missingBefore the mistake it had enough information, and chose a plausible wrong answerYes, this is the raw material
It was a one-offA fresh session does the same work correctlyCollect more samples first
Nobody can sayNeither you nor the agent knows what counts as correctNo, write the grading rule first

The original puts the second row better. The difficulty cannot come from a requirement the user only adds afterwards. Someone working from the information available before the mistake should have a chance to spot it or avoid it.

Two multipliers decide whether the task is worth building, how large the gap is between the model and a human expert, and whether the problem carries economic value. Large on both counts and it is worth starting.

2. Find, by sending the agent through your own traces#

The traces are already on disk. Claude Code writes under ~/.claude/projects/, one .jsonl per working directory. Codex writes under ~/.codex/sessions. pi writes under ~/.pi/agent/sessions. On this machine those three directories hold 100 .jsonl files between them.

Do not read them yourself. Hand the filters to an agent, let it sweep, and look only at what it brings back. The four from the original are below.

  • The user said the output was not good, and it changed noticeably after rework
  • The user and the agent went several rounds on one question, and the agent has a long trace on it
  • The difficulty is not missing user information. One specific, plausible wrong decision can be located, and the information available before it was enough to avoid it
  • The task has a defined input, a deliverable, and a checkable standard

Then look at the candidates yourself. Those four judge shape, not value, and the half about being both valuable and hard in your own field is yours to supply.

3. Cut, from the moment before the mistake to the unwanted deliverable#

A session is a mess of things, reading papers, designing an experiment, running the compute, writing it up. The stretch that produced the gap is usually one part of it.

The cut opens at the moment before the model made the mistake, and closes when the unwanted deliverable was finished. Both ends land on a specific line of the trace, not on a feeling.

Current models are rarely wrong in the absolute sense, and mostly pick a plausible wrong answer. The original suggests letting an agent locate the window while you confirm that what it hands back is a task with a defined input and output.

4. Rebuild the environment as an image#

Two pieces have to be restored. The first is everything the model knew before the window opened, compressed into an instruction plus a starting workspace. The second is the dependencies, the specialist software and libraries such as blender or lean, baked into one image.

Copy the shape from terminal-bench. It is one directory per task now, five parts.

my-task/
├── instruction.md      # what the agent is told
├── task.toml           # metadata, resources, timeouts
├── environment/        # Dockerfile, the starting workspace
├── solution/           # solve.sh, the oracle that proves it is solvable
└── tests/              # test.sh, the grading

The lines in task.toml that matter, taken from bun-sourcemap-leak in that repo, version 2.2.0.

[metadata]
expert_time_estimate_hours = 1.5

[verifier]
timeout_sec = 600.0

[agent]
timeout_sec = 28800.0

[environment]
cpus = 2
memory_mb = 4096
storage_mb = 10240

Keep the two timeouts apart. 28800 seconds is the ceiling on one agent trial, eight hours. 600 seconds is the ceiling on the grading step.

expert_time_estimate_hours says 1.5 because TB takes a task only if an expert who knows the answer can finish it in a few hours. The guidelines add that difficulty should not be measured by how much work there is to do, so when that field reaches two digits the thing to re-read is usually the steps in the task and not the knowledge in it.

5. Run it in a clean context#

A written prompt is not yet a working task. Give it to a new agent in a clean context and watch whether it fails where you expected it to.

Clean means two things. Do not reuse the context that just accumulated, which the comments on the original raised as the worry that writing the task and answering it yourself ends in a suspiciously perfect score. The author’s reply was a fresh session, or a subagent. Clean also means fair. The prompt is written by a person, the environment has to be reproducible, and everything needed goes into a shared environment, so that every model sees the same thing at the start. That answer came from the author in the same comment thread.

Four explanations in the original cover a run that does not reproduce what you expected.

  • The prompt and the environment did not restore the original failure. Send the agent back for a diff
  • The failure belonged to an older model, and the current one gets it right
  • It was a one-off, and several runs all pass, which means the task has no difficulty left
  • The prompt hints too much, and makes business judgements the model should be making

The third needs sampling. One failing run says little, and a model that clears several runs has saturated the task for you. TB’s maintenance rules retire saturated tasks in a major release.

Running the public set looks like this, four jobs at a time.

harbor run --dataset terminal-bench@2.0 \
  --agent claude-code \
  --model <model> \
  --n-concurrent 4

Your own task runs in the same framework, where one attempt is one trial.

6. The verifier has to be tested too#

The score cannot be improvised. Write the grading rule the way an exam is graded, a 1/0 pass or fail, or a continuous 0 to 100. Both failure directions have to be guarded, since a false negative kills a good answer and a false positive lets a bad one through. Add an oracle solution that scores full marks, which proves the task is solvable at all.

Harbor writes the score to a fixed path inside the container.

/logs/verifier/reward.txt      # one number
/logs/verifier/reward.json     # several dimensions, or labelled ones

The guidelines have one sentence about the verifier, quoted here.

The verifier needs to be almost perfect, but not provably perfect.

Another reads more like a test of the prompt itself. Two reasonable people who read the task description should write graders that pass the same solution, and if they do not, the description is missing something. The original wording is “if two reasonable people read the problem description, a well-specified problem should result in both of them writing verification algorithms so that anyone who passed one of the verifiers would also pass the other.”

An LLM judge is the exception in those guidelines, not the default. Reaching for one means showing it is almost never wrong, and writing down why the alternatives were not enough.

7. Read the trace, which is the whole of eval engineering#

The original says the essence of eval engineering is reading trajectories. Hand the model’s run to an agent, ask the five questions, and where to change the task is usually obvious.

What you seeWhat it meansWhat to change
It fails, stuck on a plausible wrong answerThe difficulty is realNothing, keep it
It fails, stuck on an environment that will not installThe setup is brokenThe image
It succeeds along a path that looks identical every timeThe prompt hints too muchinstruction.md
The trace solves it and the grade says noThe verifier is too narrowtests
The steps pile up in one placeWhere the difficulty sitsWhether to cut it smaller

8. Do not make it long for the length#

The question comes up of how long a task should run, and whether longer is better. The original says not necessarily. Stack several hard points mechanically and the model is unstable on each of them, so an end-to-end deliverable becomes close to impossible. From a training point of view the signal is too sparse, and unstable.

The split it offers takes one large task A and breaks it into stages B, C and D. If the model cannot do B, C or D on its own, making each of them a task is worth more than swallowing it whole. If each of them passes and A still fails, then A has earned its own task.

9. The raw material is domain knowledge#

Terminal-Bench 2.0 holds 89 tasks, and the repository carries 52 task directories today, which is the whole pool a public leaderboard can pull from.

The original is blunter. The hottest leaderboards have probably been trained against, and the quiet ones are usually bad, or they would not be quiet. So before adding another verifiable benchmark, ask whether it can be done better than terminal-bench. Internal evals should run ahead of the public ones, and the difference comes from out-of-distribution scenarios and from more human judgement.

It closes with one aside. Several model companies are handing out free tokens to researchers, and what they want is to sift tasks out of your traces. You can do that job better yourself, because the context of your workspace is in your hands.

Two questions I cannot answer yet.

  • How low the human cost of one task, from a trace to something shippable, can go. The original gives no number.
  • How large a gap between an internal eval and a public leaderboard is normal. Nobody publishes it.

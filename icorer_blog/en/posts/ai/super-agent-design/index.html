Super-agent: DeepSeek Takes Sessions Away From the User

Posted by LB on Mon, Nov 2, 2026
中文版是这篇文章的默认版本。 阅读中文版 →
This English page stays available at this URL; the Chinese version is the one we maintain first.

In one line: the interesting claim in DeepSeek Harness’s architecture note is not its five modules — modules change with deployment. It is one sentence: sessions should be an implementation detail of the system, not a mental burden on its user. Everything below is that sentence, taken seriously.

Published 2026-10-31, the note opens by telling you what it is not: an architecture discussion, not a description of shipping features. The prototype went up on GitHub the same day, MIT-licensed, with a README that says the same thing more bluntly — research code, not equal to the internal version. Read it as a paper first, as a product spec second. The two readings disagree, and the disagreement is the useful part.

1. The problem: the bottleneck moved to attention

The authors’ observation is small and sharp:

The ceiling on a single task is model capability; the ceiling on many tasks is human attention. In our experience one person can follow only 3 to 5 active sessions at once.

No method, no sample — but anyone who has run three agents in parallel will recognise it. The reason is not laziness. It is that today’s agents weld two jobs onto one object:

What a session isWhat that costs
the container of the model’s contextyou cannot switch without paying to rebuild context
the user’s unit of project managementso “close the session” means “lose the project”

Three structural limits follow: a single session blocks on long operations, contexts from different tasks contaminate each other, and everything stops when the laptop sleeps. CLIs, MCP servers and connectors do not touch any of the three, because the problem is not the interface — it is that the session was made the boundary of the system.

2. What it proposes: five modules

Four properties are claimed — continuous, productive, proactive, persistent — and no single ReAct loop can deliver them. So they land on different modules:

PropertyWhat buys itWhat breaks without it
Continuoustwo layers, all channels funnelled through the Routeryou become the one who remembers which session saw which sentence
Productivecontext-isolated workers running in parallelone task at a time
ProactiveTriggers, two-stage filtering, speculative worka more expensive command line, still waiting for orders
Persistentcompute/state split, endpoint daemons, a watchdoga laptop lid ends the work

The design does not claim to invent anything. It maps classic computer-systems ideas — two-level scheduling, fast and slow paths, treating the context window as a cache, speculative execution, compute-storage separation, an external control loop — onto an agent system. That framing is the honest one, and it tells you how to read the rest: for each analogy, ask where it holds and where it breaks.

3. Two layers: a Router that only dispatches

Continuity and throughput are a genuine trade-off. Send every event to one session and the context is maximally continuous, but a ReAct loop runs one step at a time, so throughput collapses and the details of unrelated tasks interleave. Give every event a fresh session and throughput is maximal, but related work loses its shared context and several sessions talk to the user at once. The note splits the cost across two layers instead of trying to beat it.

The Router layer carries three hard constraints:

  1. It does not execute tasks. Interaction and dispatch only — “it can run without a Bash tool at all”.
  2. It is the global sequence point, coordination point and memory. Everything cross-task converges there.
  3. It can be a lighter model. The note’s claim is that Router work “is often simpler than expected”.

The third has a non-obvious support: batching. Triggers that queue during one inference turn are merged into the next call. The Router’s steps are long input, short output, and merged triggers are computed in parallel during prefill — so up to a point, the deeper the backlog, the lower the amortised inference time per decision. Section 7 shows the measurement.

The difference from an Agent Team is worth a table, because the two get conflated constantly:

Agent TeamA Super-agent’s two layers
Who decomposes the workthe lead splits subtasks and coordinates oftenthe Router never splits; workers derive requirements from the raw event
Where the reasoning load sitsheavy, on the leadlight on the Router, heavy on each worker
Failure modethe lead misreads the task, everyone driftsworkers drift separately; the Router only sees progress or its absence
Can you get there from a Team—yes: forbid the main session to execute work, leave it interaction plus dispatch

That last row is the practical one: the two-layer architecture is a prompt constraint plus a main session that does not do the work. You can try it without changing frameworks.

The cost is visible in the prototype’s prompts. Because the Router must not decide for the worker, prompts/dispatch.md is a wall of prohibitions:

Do not expand a request’s scope, add implementation plans, acceptance criteria or policy checklists… Do not paraphrase a short request into a work plan, pick examples or categories, invent requirements…

It even carries the example: “Could we add a dark mode?” must arrive as that request, with its source reference, and no Router-chosen colour scheme. The verbosity of that prompt is the receipt: being light is not free; it is paid for by writing down “do not get clever” as a rule.

4. Event-driven: one Trigger’s life

The input is no longer a prompt someone types. It is a semi-structured event: a group message, a pull-request comment, a CI result. The note walks one event from arrival to action in four increasingly specific steps.

Filtering. A programmatic gate takes deterministic conditions — source, group, allowlists — and drops most traffic before any model call. What survives goes to a semantic gate: a model deciding against policy written as prompts. The prototype keeps the two genuinely separate: src/admission.ts is an admission matrix over “listed or not” and “addressed or not” (three cells; a listed sender who addresses the agent is always an explicit request), defaulting hard to caution, and the semantic half lives in src/app/assessment.ts.

Routing. Consecutive events on the same pull request, IM thread or email chain form a Thread. The Router only handles cold starts: it creates the worker for a thread’s first event and subscribes it. After that, code passes follow-ups straight through; the Router can still see them, but does not forward them. Subscriptions are many-to-many, which is how two workers that touch the same PR learn about each other without point-to-point messaging.

Pass-through does not buy speed; it buys the Router’s budget. Remove it and completion time barely moves (12.6 / 15.5 minutes against 12.4 / 15.7), while the Router makes about 30% more decisions and cache-read tokens rise from 23.2M to 31.8M.

Context. The window is treated as a cache. Inline what is needed soon; spill what is not, leaving a pointer and a summary behind, then walk the reference graph hop by hop when a question reaches back.

In code this is plain but real: preview() in src/app/cards.ts compresses a body to 160 characters, and the card carries an id plus read: ticket/<id>; inputLine() inlines up to 80 characters and leaves a pointer beyond. The thresholds are guesses; the direction is right. What is missing is the multi-hop part — relatedTickets hops once, and the article’s reference graph has no implementation yet.

Speculation. Act before the outcome is known to be useful: when someone reports an issue, reproduce it and look for a cheap fix in the background, speak only once the problem is confirmed. The prototype’s version of this is a good product decision — proactive work starts in a mode that only records what the agent would have done, so you can read the intent before granting the action.

5. The human side: full duplex, many channels

A classic ReAct loop calls run() synchronously: until the tool returns, the session hears nothing. Make the call asynchronous — start() returns Started at once, the result arrives later as a new event — and the foreground stays available while work continues.

Then the note says something worth quoting exactly:

DeepSeek Harness already implements this asynchronous task mechanism, but it is not yet enabled by default.

So full duplex is a switch, not the default interaction contract — and the felt experience of the whole system depends on that switch.

The multi-channel half is more immediately copyable. Two rules:

  • Instant messaging: behave like a colleague — notify only when a decision or sign-off is needed, ask direct questions, give short conclusions. Their hard rule is 100 words per reply.
  • Asynchronous channels (GitHub, email, documents): structured, information-dense delivery — full problem background, what changed, how it was verified.

The hundred-word rule is not a style guide in the prototype; it is transport-enforced. prompts/replies.md says “100 words is a hard ceiling, not a writing target”, and the transport rejects longer IM messages, including when someone asked for technical detail. A constraint the system can execute beats a request to “be concise”.

6. Persistence: brain in the cloud, hands where they are

A local agent welds three things to one machine: the compute that runs the loop, the state that must survive, and the execution environment — repositories, toolchains, credentials. Close the lid and all three stop.

The note decouples in two steps. First, compute becomes stateless containers and session state moves to a database, so the agent stops sharing a machine’s lifetime. Second, the cloud loop is separated from the heavy execution environment: the endpoint runs a daemon that keeps no session state, executes commands and returns results.

This is Anthropic’s brain/hands split, reached from a different starting point:

Anthropic Managed AgentsDeepSeek Super-agent
What it connects firston-demand sandboxes, customer VPCsthe developer’s own machine, uncommitted work included
Availability assumptioncloud and sandbox are upthe endpoint may be online only intermittently; tasks resume on reconnect
Security approachtokens never reach the sandbox: git tokens wired into the remote at init, MCP through a vault and proxylisted as an open problem (§8.4)
Published payoffTTFT p50 −60%, p95 −90%+ (vendor-published)no numbers for the split

That last row is the interesting asymmetry: one side reports a latency number, the other reports a design. The latency number is what makes the split more than architecture hygiene — it lands on the part users feel.

The watchdog is the other half of persistence: not a liveness probe, but a session outside the main system, driven by scheduled messages, with the full toolset. It fixes infrastructure failures and asks a model whether each worker is making substantive progress or drifting from the goal. Maintainers can ask it, in natural language, why something failed — and have it edit prompts or trigger rules while the system runs. Supervising agents with an agent is elegant on the happy path; see section 9 for the other path.

Two experiments, both synthetic: about 300 messages per run with about 20 work requests, coding replaced by a tool that only consumes time, five runs per design.

Three things have to be read together:

  1. It measures scheduling, not execution. A timer stands in for coding, so “12.4 minutes” contains no written code. These numbers support “two layers are more stable than one session”; they do not support “the work is better”.
  2. The single-session row is a story about prompts, not models. With a neutral prompt the model delegated in none of five runs and p95 hit 29.5 minutes; told to prefer delegation it delegated in four of five, and the fifth judged the work “small” and did it itself — the long tail in the figure. Leaving “should I split the work?” to prompt engineering and on-the-spot judgement is exactly the fragility the two-layer design removes.
  3. The tokens are real money. 23.2M against 6.1M is 3.8×. The note says it plainly: more tokens buy shorter, more stable completion times.

The summary of that table: the prototype finishes routing and authorization, and leaves persistence and self-healing on paper. Those two are the hard ones — one changes deployment, the other changes operations.

Two details say more about the engineering than the module diagram does. The domain model is far more verbose than the article: eleven concepts in docs/001-domain.md, plus a table of rejected concepts — “at most one ticket per thread” is rejected because a thread can carry several unrelated pieces of work. And authorization is separated from context: a trigger reaching a ticket is context, granting nothing; what authorizes work is an immutable Mandate on the ticket — who authorized, under which policy version, how far it may go. The article does not stress this, but it is the precondition for being proactive safely.

9. Where it does not hold

Security is not an open problem, it is a precondition. Section 8.4 admits the design assumes cloud and endpoints trust each other, and that a compromised loop puts every connected device at risk. That is not hypothetical: Tencent’s A.I.G measured indirect-injection success against DSH over 14,560 controlled runs at 17.0% (text mode, semantic judge), 25.5% (file mode, hidden Unicode, rule judge) and 16.0% (skills channel, file mode). At that order of magnitude, in a “cloud loop plus endpoints holding credentials” structure, one injection is roughly one set of devices. Anthropic’s structural answer — credentials never enter the sandbox — is worth copying; DeepSeek states the problem and stops.

The watchdog is an attack surface. It shares the system’s permissions and can edit prompts and trigger rules live. Supervising an agent with an agent is elegant until the supervisor is injected; the note does not discuss it.

Long-horizon memory is the real ceiling. Section 8.1 says chain-of-recall handles recent tasks and session history; once the system runs for months, memory is the bottleneck. Recall and memory are different problems — finding something is not the same as knowing what to keep and what to forget.

“3 to 5 sessions” has no method. It is the premise of the entire motivation: no sample, no measurement. It may well be right; as a foundation, it is self-reported.

Synthetic load has a ceiling. A timer, 1/4-scaled durations, five runs. Enough for “scheduling helps”, not enough for any absolute time. The note says so itself.

Complexity moves, it does not disappear. The design takes session management away from the user — good. But the system’s own complexity has to land somewhere, and DSH’s own reception suggests it lands on the operator. Add one more layer and the user loses the handle on what the agent is doing: section 8.2 admits that presenting tasks without sessions is unsolved. Traceable mandates and auditable decision records may matter more than another architecture diagram.

And a methodological note. Attention is the only thing being optimised here. That is right for parallel work, and it systematically undercounts a second need: understanding what happened, why, and whether it can be reproduced. Saving attention and staying explainable pull in opposite directions, and this note only does the arithmetic on one side.
